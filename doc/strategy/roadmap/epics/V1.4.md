# V1.4: C ABI

**Labels:** `type/epic`, `type/enhancement`, `area/platform`
**GitHub Issue:** TBD

Freezes a language-neutral interface that exposes the proven runtime capabilities through C-callable functions. Uses Arrow's C Data Interface structures for array/table interchange, exposes normalized backend status/error information as stable C types, and provides opaque handles for backend state such as solvers or RNGs. ABI compatibility tests detect accidental binary-interface breakage across releases.

## Product Intent

Deliver the C ABI: a language-neutral interface that exposes Yamori's runtime capabilities — dependency graph, backend router, shared memory — through stable C-callable functions. The outcome is that any language (Python, Rust, Go, JavaScript) can consume Yamori's capabilities through a frozen, documented C interface without depending on C++ headers or build systems.

## Users And Jobs

- [Python developer]: Import Yamori's capabilities from Python via the C ABI — no C++ compilation required.
- [Rust developer]: Link against Yamori's C ABI for zero-cost interop with Rust's type system.
- [Compliance reviewer]: Verify that the C ABI is frozen and documented — no undocumented function signatures or type changes.
- [Investment analyst]: See the same results whether consuming Yamori from C, Python, or Rust — the ABI guarantees parity.

## Success Metrics

- All runtime capabilities exposed through C-callable functions — no C++ headers required for consumers.
- Arrow's C Data Interface used for array/table interchange.
- Backend errors exposed as stable C types — no C++ exception types in the ABI.
- Opaque handles for backend state (solvers, RNGs) — consumers never see implementation types.
- ABI compatibility tests detect accidental binary-interface breakage across releases.
- Consumable from Python for research→production parity validation.

## Demo Moment

- Command or flow: A Python script that calls `yamori_valuation_run()` through the C ABI and prints a per-share intrinsic value.
- Expected result: A Python process consuming Yamori's capabilities via the C ABI, producing the same results as the C++ library.

## Scope

### In Scope

- C function declarations: all runtime capabilities exposed as C-callable functions.
- Arrow C Data Interface: array/table interchange via `ArrowSchema` and `ArrowArray`.
- Error types: stable C types for Yamori status/errors — no C++ exceptions.
- Opaque handles: backend state (solvers, RNGs, shared memory) exposed as opaque pointers.
- ABI compatibility tests: detect accidental binary-interface breakage across releases.
- Python consumption: a working Python binding via the C ABI for validation.
- Provenance: every ABI-exposed function documents its contract, types, and error conditions.

### How Many Stories?

Seven stories: C declarations (S1), Arrow C Data (S2), error types (S3), opaque handles (S4), ABI tests (S5), Python binding (S6), and documentation (S7). Each delivers an independently testable layer of the C ABI. The scope is narrow (one ABI surface), so 7 stories reflects the number of distinct ABI capabilities.

### Decomposition Rules

1. **Independent delivery**: Each story compiles and produces a verifiable artifact (C header, test, binding).
2. **One capability per story**: S1 = declarations; S2 = Arrow C Data; S3 = errors; S4 = handles; S5 = tests; S6 = Python; S7 = docs.
3. **Split by capability lifecycle**: S1–S4 establish the ABI surface; S5–S7 verify and document it.
4. **Closure story**: S7 ensures every ABI function is documented — the consumer contract.

### Bad Splits (Avoid)

- "C declarations" + "Arrow C Data" as two stories. The C declarations include the Arrow C Data types — they are one interface surface.
- "Python consumption" + "ABI documentation" as two stories. Python binding is the validation; documentation is the contract. They are tightly coupled.

### Story Line Format

Story IDs follow `VX.Y.SN`. Each story is independently compilable and testable.
