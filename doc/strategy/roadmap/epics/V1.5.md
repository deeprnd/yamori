
# V1.5: Guaranteed Reproducibility

**Labels:** `type/epic`, `type/enhancement`, `area/platform`
**GitHub Issue:** TBD

Delivers the most difficult claim Yamori can make: bit-identical results across all target platforms for the same inputs. Every algorithm is pinned to a specific, deterministic implementation. Every random operation uses an explicit seed. Every floating-point reduction uses a fixed order. The result is a system where reproducibility is structural — not a testing goal, but a runtime guarantee. When a user runs a valuation on Linux x86 and another runs the same valuation on macOS ARM with the same data, the results are identical — not approximately, but bit-for-bit.

## Product Intent

Deliver the reproducibility framework: a built-in guarantee that Yamori produces bit-identical results across all target platforms (Linux x86, Linux ARM, macOS ARM, Windows x86) for the same inputs and dataset manifest. The outcome is absolute trust: users know that sharing a valuation means sharing an exact number, not a number that "should be close." Every algorithm, random operation, threading decision, and floating-point reduction is pinned to a deterministic implementation — determinism is a runtime capability that every downstream feature inherits, not a testing exercise.

- [Investment analyst]: Share a valuation with a colleague and know they will see the exact same numbers when they run it — reproducibility is guaranteed, not hoped for.

### How Many Stories?

Seven stories: algorithm pinning (S1), RNG pinning (S2), threading policy (S3), reduction order (S4), fast-math (S5), cross-platform harness (S6), and provenance (S7). Each delivers an independently testable layer of the determinism framework. The scope is narrow (one policy surface), so 7 stories reflects the number of distinct determinism controls.

### Decomposition Rules

1. **Independent delivery**: Each story compiles and produces a verifiable artifact (pin, policy, harness).
2. **One capability per story**: S1 = algorithms; S2 = RNG; S3 = threading; S4 = reduction; S5 = fast-math; S6 = harness; S7 = provenance.
3. **Split by capability lifecycle**: S1–S5 establish the determinism controls; S6–S7 verify and document them.
4. **Closure story**: S7 ensures every deterministic result records its provenance — the audit layer.

### Bad Splits (Avoid)

- "Algorithm pinning" + "RNG pinning" as two stories. They are both pinning controls but independently verifiable.
- "Threading policy" + "Reduction order" as two stories. They are both concurrency controls but independently testable.

### Story Line Format

Story IDs follow `VX.Y.SN`. Each story is independently compilable and testable.
