# V5.25: Deterministic Audit Trail and Provenance Hash

**Labels:** `type/epic`, `type/enhancement`, `area/finance`, `area/audit`
**GitHub Issue:** TBD

A valuation without a provenance hash is just a number. V5.25 captures the complete audit trail for every valuation: dataset manifest hashes, policy field values, source document citations, adjustment decisions, and provenance chains for every computed metric. It produces a `provenance_hash = BLAKE3(canonical(inputs) || policy || semver || dataset_manifest)` for machine-checkable reproducibility. Golden tests assert on provenance hashes, not just numeric outputs. The outcome is that every valuation can be independently verified by any third party — the provenance hash is a single value that encodes every input, policy decision, and dataset version used in the computation.

## Product Intent

Deliver the deterministic audit trail and provenance hash engine: capture the complete audit trail for every valuation (dataset manifest hashes, policy field values, source document citations, adjustment decisions, provenance chains), produce a `provenance_hash = BLAKE3(canonical(inputs) || policy || semver || dataset_manifest)` for machine-checkable reproducibility, and use provenance hashes in golden tests. The outcome is that every valuation carries a single hash value that any third party can verify against their own computation — the ultimate determinism guarantee.

## Users And Jobs

- [Investment analyst]: Verify any valuation by recomputing the provenance hash and comparing it to the published hash — proving the valuation was computed from the exact inputs claimed.
- [Compliance reviewer]: Verify that the provenance hash encodes all inputs, policy decisions, and dataset versions; that golden tests assert on hashes, not just numeric outputs.
- [Engineer]: Extend the provenance hash by adding new input dimensions (e.g., new adjustment types) without changing the hash structure.
- [Tickoni tile]: Consume `computeProvenanceHash(valuation_inputs)` as a callable pivot that returns the provenance hash for machine-checkable reproducibility.

### How Many Stories?

Four stories: audit trail (S1), hash computation (S2), golden tests (S3), and machine-checkable verification (S4). The hash computation is the credibility signal — it deserves its own story.

### Decomposition Rules

1. **Independent delivery**: Each story produces verifiable audit output.
2. **One capability per story**: S1 = trail capture; S2 = hash; S3 = tests; S4 = verification.
3. **Split by capability lifecycle**: S1 captures the data; S2 computes the hash; S3 validates; S4 proves reproducibility.
4. **Closure story**: S4 returns machine-checkable reproducibility with provenance.

### Bad Splits (Avoid)

- "Audit trail" + "Provenance hash" as two stories. They are the same capability — the hash is derived from the trail.

### Story Line Format

Story IDs follow `VX.Y.SN`. Each story is independently compilable and testable.
