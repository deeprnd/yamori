
# V5.22: Batch Valuation Runner

**Labels:** `type/epic`, `type/enhancement`, `area/finance`, `area/build`
**GitHub Issue:** TBD

Executes M2's `runValuation()` pipeline across a peer set in a single batch operation. Shares dataset manifest lookups and policy objects across runs to minimize redundant computation. Produces a peer-set valuation table with all M2/M3/M4 outputs for every company, enabling cross-company comparison from a single execution. Uses M1's shared-memory representation for zero-copy data sharing across batch runs. The outcome is that an entire peer set can be valued in one command — not a spreadsheet of individual runs, but a unified table of results ready for comparative analysis.

## Product Intent

Deliver the batch valuation runner: execute M2's `runValuation()` pipeline across a peer set in a single batch operation, sharing dataset manifest lookups and policy objects across runs to minimize redundant computation. Produce a peer-set valuation table with all M2/M3/M4 outputs for every company. Use M1's shared-memory representation for zero-copy data sharing across batch runs. The outcome is a single command that values an entire peer set and produces a unified comparison table.

## Users And Jobs

- [Investment analyst]: Run a valuation across an entire peer set in one command and get a unified table of intrinsic values, multiples, and audit assertions — ready for comparative analysis.
- [Compliance reviewer]: Verify that all companies in the peer set were valued using the same policy settings and dataset vintages.
- [Engineer]: Extend the batch runner by adding parallel execution for large peer sets without modifying the single-company pipeline.
- [Tickoni tile]: Consume `batchValuate(peer_set_name)` as a callable pivot that returns a peer-set valuation table.

### How Many Stories?

Four stories: batch orchestration (S1), zero-copy sharing (S2), output table (S3), and deterministic execution (S4). The batch runner is the execution engine — essential for comparative analysis.

### Decomposition Rules

1. **Independent delivery**: Each story produces verifiable batch layer.
2. **One capability per story**: S1 = orchestration; S2 = data sharing; S3 = output; S4 = determinism.
3. **Split by capability lifecycle**: S1 orchestrates the batch; S2 shares data; S3 formats output; S4 guarantees determinism.
4. **Closure story**: S4 returns deterministic batch execution with shared memory.

### Bad Splits (Avoid)

- "Batch orchestration" + "Zero-copy sharing" as two stories. They are the same capability — orchestration requires data sharing.

### Story Line Format

Story IDs follow `VX.Y.SN`. Each story is independently compilable and testable.
