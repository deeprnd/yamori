# V1.1: Core Types, Policy, and Valuation Runner

**Labels:** `type/epic`, `type/feature`, `area/investing`
**GitHub Issue:** TBD

The Damodaran engine cannot execute until it has domain types, error semantics, policy inputs, and the pure `runValuation()` pivot. V1.1 establishes the structural foundation: currency-typed `Money<C>`, `Rate`, `Period`, `DataPoint<T>`, `ValuationPolicy`, the `!Error` return convention throughout, and the pure `runValuation(inputs, policy) -> ValuationResult` function that all downstream analyses (sensitivity, scenarios, reverse DCF, Monte Carlo) call as a black box. Without this foundation, every downstream epic is a collection of disconnected calculations with no unified entry point.

## Product Intent

Deliver the first self-contained execution surface of the Damodaran DCF engine: a pure function that accepts structured financial inputs and a policy record, runs the complete valuation pipeline, and returns a typed result. The outcome is that Yamori can compute one deterministic valuation from scratch — not a demo, but the first Tickoni capability that produces an auditable, reproducible intrinsic value from raw financial data.

## Users And Jobs

- [Investment analyst]: Run a complete Damodaran valuation on a public company and receive a per-share intrinsic value with full intermediate outputs.
- [Compliance reviewer]: Verify that the valuation pipeline is deterministic and reproducible by re-running the same inputs and checking the output hash.
- [Engineer]: Extend the engine with new analysis (sensitivity, scenarios) by calling the single `runValuation()` pivot without re-implementing the valuation formula.
- [Tickoni tile]: Consume `runValuation()` as a callable capability from shared memory or via the C ABI without knowing the internal module layout.

## Success Metrics

- `runValuation()` is pure: no I/O imports in `valuation_core`; compiles with zero file-access symbols.
- Currency mixing fails at compile time via `Money<C>` phantom type.
- All public functions return `!Error`; no `unreachable` in library code.
- Bit-identical output across Linux x86, Linux ARM, macOS ARM, and Windows x86 for the same inputs and dataset manifest.
- Golden test produces a verified per-share intrinsic value within 0.01% of the methodology's reference calculation.

## Demo Moment

- Command or flow: `tickoni valuation run STLA --dataset-manifest datasets/manifest.toml --policy policy.json`
- Expected result: A `ValuationResult` with per-share intrinsic value, WACC, growth stages, and FCFF schedule, all deterministically reproducible across platforms.

## Scope

### In Scope

- Domain types: `Money<C>`, `Rate` (with `fromBps`/`fromPercent`), `Period`, `DataPoint<T>`.
- `ValuationPolicy` record with all Step 1 policy fields.
- `!Error` return convention; error enum with typed variants.
- Pure `runValuation(inputs, policy) -> ValuationResult` pivot function.
- Module architecture: `valuation_core` with no I/O imports; structural purity enforced at compile time.
- Cross-platform bit-identity test harness.
- D3 lint set: no `std.math.pow` for discount factors; fixed summation order; no fast-math.

### Out Of Scope

- Financial statement ingestion (V2.11).
- Accounting adjustments: R&D capitalization, lease capitalization, SBC (V2.7–V2.9).
- Dataset normalization and manifest (V5.25).
- Reverse DCF, sensitivity, scenarios, Monte Carlo (V3.12–V3.15).
- Peer-set management and comparative analysis (V4.17–V4.21).
- Report generation and export (V5.232).
- CLI and MCP server interfaces (V5.26).

### How Many Stories?

Four stories: types (S1), policy+error (S2), the valuation function itself (S3), and the determinism guarantee (S4). Each delivers an independently testable outcome. S1 compiles; S2 validates policy schema; S3 produces a valuation; S4 proves cross-platform identity.

### Decomposition Rules

1. **Independent delivery**: Each story compiles and produces a verifiable artifact (type definitions, policy validation, valuation output, bit-identity test).
2. **One capability per story**: S1 = types; S2 = policy+errors; S3 = the function; S4 = determinism. No story mixes unrelated capabilities.
3. **Split by capability lifecycle**: S1–S2 establish the type system; S3 builds the function; S4 verifies the guarantee.
4. **Closure story**: S4 includes the bit-identity test that closes the epic's determinism claim.

### Bad Splits (Avoid)

- "Types" + "Policy" as one story. Types and policy serve different purposes and are consumed independently.
- "runValuation()" + "bit-identity test" as one story. The function and its cross-platform guarantee are independently testable.

### Story Line Format

Story IDs follow `VX.Y.SN`. Each story is independently compilable and testable.
