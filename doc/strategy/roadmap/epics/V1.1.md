# V1.1: Financial Formula Dependency Graph

**Labels:** `type/epic`, `type/enhancement`, `area/platform`
**GitHub Issue:** TBD

Defines financial metrics as named dependency graphs over source metrics; derived metrics resolve in deterministic topological order without performing numerical work themselves. The graph enables sensitivity analysis, Monte Carlo simulation, and reverse DCF because `runValuation()` traverses the graph rather than calling a monolithic function. Named formulas describe a derived metric by name, required source metrics, and backend operations. This is Yamori's strongest differentiator: the graph, not any single formula, is the reusable asset.

## Product Intent

Deliver the financial formula dependency graph: a runtime that understands financial meaning — not just `divide(a, b)` but `IntrinsicValue depends on FCFF depends on EBIT depends on tax...` — and can re-evaluate any subset of the graph when inputs change. The outcome is a named formula registry and topological resolver that makes every downstream analysis (sensitivity, Monte Carlo, reverse DCF) a single graph traversal rather than a reimplementation.

## Users And Jobs

- [Investment analyst]: Define a derived metric by referencing other metrics and see it compute automatically from the dependency graph.
- [Compliance reviewer]: Trace any computed metric back through its dependency graph to its source data, verifying every computation path.
- [Engineer]: Add a new financial formula by defining its dependency graph and backend mapping, without touching any numerical kernel.
- [Tickoni tile]: Consume `resolveAndCompute(name)` as a callable pivot that returns a computed metric with full dependency provenance.

## Success Metrics

- Named formulas defined by source metric names, operations, and backend function identifiers.
- Dependency resolution in deterministic topological order — no forward reference, no cycle.
- `runValuation()` traverses the dependency graph rather than calling a monolithic function.
- Sensitivity analysis: change one leaf metric and re-evaluate the entire graph.
- Monte Carlo: sample leaf inputs, re-evaluate the graph for each sample.
- Reverse DCF: solve over one graph input given a target output.
- Every computed metric carries its dependency chain and formula definition.

## Demo Moment

- Command or flow: `tickoni formula define ROIC --sources NOPAT,InvestedCapital --op divide --output frame`
- Expected result: A computed ROIC series derived from NOPAT and InvestedCapital via the dependency graph, with full provenance.

## Scope

### In Scope

- Named formula definition: describe a derived metric by name, required source metrics, and backend operations.
- Dependency resolution: resolve derived-metric dependencies in deterministic topological order.
- Cycle detection: reject circular dependency definitions at definition time.
- `runValuation()` integration: the valuation runner traverses the graph rather than calling a monolithic function.
- Graph re-evaluation: change one leaf metric and recompute only the affected subtree.
- Provenance: every computed metric carries its formula definition and dependency chain.
- Integration with Arrow Compute: backend operations map to Arrow Compute function identifiers.

### Out Of Scope

- Historical metrics: NOPAT, invested capital, ROIC from statements (M2, V2.1–V2.2).
- Cost of capital: WACC, beta, CRP (M2, V2.3).
- Three-stage growth model (M2, V2.4).
- Terminal value and equity bridge (M2, V2.5).
- Sensitivity and scenario analysis (M4, V4.14–V4.15).
- Monte Carlo engine (M4, V4.17–V4.20).
- Reverse DCF solver (M4, V4.12).
- Financial statement ingestion (M3, V3.6–V3.11).

### How Many Stories?

Seven stories: named formula (S1), resolution (S2), cycle detection (S3), Arrow adapter (S4), graph traversal (S5), re-evaluation (S6), and provenance (S7). Each delivers an independently testable capability. The scope is infrastructure-level (the graph engine itself), so 7 stories reflects the number of distinct graph operations.

### Decomposition Rules

1. **Independent delivery**: Each story compiles and produces a verifiable artifact (schema, resolver, adapter, traversal).
2. **One capability per story**: S1 = schema; S2 = resolver; S3 = cycle detection; S4 = Arrow adapter; S5 = traversal; S6 = re-evaluation; S7 = provenance.
3. **Split by capability lifecycle**: S1–S3 establish the graph schema and resolver; S4–S6 connect the graph to execution; S7 adds provenance.
4. **Closure story**: S7 ensures every computed metric carries provenance — the evidence layer.

### Bad Splits (Avoid)

- "Named formula" + "Arrow adapter" as one story. Schema and backend mapping are independently testable.
- "Graph traversal" + "Re-evaluation" as two stories. They are the same execution path with different input conditions.

### Story Line Format

Story IDs follow `VX.Y.SN`. Each story is independently compilable and testable.
