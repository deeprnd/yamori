# V4.17: Peer-Set Management and Company Catalog

**Labels:** `type/epic`, `type/feature`, `area/investing`, `area/operations`
**GitHub Issue:** TBD

M1-M3 valuations a single company; M4 extends to a peer set. But a peer set is not a list — it is a structured input with canonical identifiers, sector assignments, and geographic exposure records. V4.17 defines peer-set membership as a sourced input (persisted, not re-guessed per run). It manages the company catalog with canonical identifiers (ISO 10383 MIC, ISO 4217 currency, ISIN/CUSIP), Damodaran sector assignments, and geographic exposure records. It ensures sector assignments are consistent across valuations to prevent beta drift. The outcome is that a peer set is a first-class data structure — not a hand-typed list of tickers — with validated identifiers, consistent sector assignments, and reproducible geographic exposure records that feed every downstream comparative analysis.

## Product Intent

Deliver the peer-set management and company catalog: define peer-set membership as a persisted, sourced input; manage the company catalog with canonical identifiers (ISO 10383 MIC, ISO 4217 currency, ISIN/CUSIP), Damodaran sector assignments, and geographic exposure records; ensure sector assignment consistency across valuations. The outcome is that peer sets are first-class data structures — reproducible, auditable, and consistent — enabling reliable comparative analysis.

## Users And Jobs

- [Investment analyst]: Define a peer set as a persisted, sourced input with canonical identifiers and consistent sector assignments — no re-guessing per run.
- [Compliance reviewer]: Verify that all identifiers are canonical (ISO 10383, ISO 4217, ISIN/CUSIP), that sector assignments match Damodaran's published taxonomy, and that geographic exposure is recorded.
- [Engineer]: Add new identifiers (e.g., SEDOL, CIK) to the catalog without modifying the core peer-set schema.
- [Tickoni tile]: Consume `resolvePeerSet(peers)` as a callable pivot that returns a validated peer set with canonical identifiers and consistent sector assignments.

## Success Metrics

- Peer-set membership: persisted, sourced input — not re-guessed per run.
- Canonical identifiers: ISO 10383 MIC, ISO 4217 currency, ISIN/CUSIP for every company.
- Damodaran sector assignments: consistent across all valuations in the peer set.
- Geographic exposure records: documented for every company.
- Sector assignment consistency: prevents beta drift across valuations.
- Peer-set validation: all identifiers verified against canonical sources.

### How Many Stories?

Four stories: persistence (S1), identifiers (S2), sector assignments (S3), geographic exposure + validation (S4). The scope is data management — foundational for all M4 capabilities.

### Decomposition Rules

1. **Independent delivery**: Each story produces verifiable peer-set data.
2. **One capability per story**: S1 = persistence; S2 = identifiers; S3 = sectors; S4 = geography + validation.
3. **Split by capability lifecycle**: S1–S2 establish the data structure; S3–S4 add sector and geography metadata.
4. **Closure story**: S4 ensures all identifiers and metadata are validated.

### Bad Splits (Avoid)

- "Canonical identifiers" + "Sector assignments" as two stories. They are part of the same data structure — the company catalog.

### Story Line Format

Story IDs follow `VX.Y.SN`. Each story is independently compilable and testable.
