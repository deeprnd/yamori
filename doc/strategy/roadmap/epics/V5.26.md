
# V5.26: Dataset Versioning and Manifest Management

**Labels:** `type/epic`, `type/enhancement`, `area/finance`, `area/build`
**GitHub Issue:** TBD

V5.26 maintains a build-time dataset manifest with per-file SHA-256 hashes, vintages, source URLs, and row counts. It handles dataset refreshes: when Damodaran datasets are updated, the manifest detects changes, flags affected valuations, and maintains version consistency across the peer set. Raw spreadsheet exports never reach the engine. The outcome is that dataset reproducibility is enforced at the infrastructure level.

## Product Intent

Deliver the dataset versioning and manifest management engine: maintain a build-time dataset manifest with per-file SHA-256 hashes, vintages, source URLs, and row counts. Handle dataset refreshes: when Damodaran datasets are updated, detect changes, flag affected valuations, and maintain version consistency. Raw spreadsheet exports never reach the engine. The outcome is that dataset reproducibility is enforced at the infrastructure level — anyone with the same inputs and dataset versions arrives at the same output.

## Users And Jobs

- [Investment analyst]: Know exactly which dataset versions were used for any valuation — and whether those versions have been updated since the valuation was run.
- [Compliance reviewer]: Verify that every dataset file has a SHA-256 hash in the manifest, that vintages match the valuation date, and that raw spreadsheet exports never reach the engine.
- [Engineer]: Add new dataset files (e.g., new Damodaran sector data) to the manifest without modifying existing versioning logic.
- [Tickoni tile]: Consume `validateDatasetManifest()` as a callable pivot that verifies dataset integrity and version consistency.

## Success Metrics

- Dataset manifest: per-file SHA-256 hashes, vintages, source URLs, row counts for every dataset file.
- Dataset refresh detection: when Damodaran datasets are updated, manifest detects changes.
- Affected valuation flagging: valuations using outdated datasets are flagged.
- Version consistency: same dataset versions across peer set.
- Raw spreadsheet exports blocked: only manifest-verified datasets reach the engine.
- Build-time manifest: datasets are validated at build time, not runtime.

## Demo Moment

### How Many Stories?

Four stories: manifest (S1), refresh detection (S2), consistency (S3), and export blocking (S4). The manifest is the foundation — everything else builds on it.

### Decomposition Rules

1. **Independent delivery**: Each story produces verifiable dataset validation.
2. **One capability per story**: S1 = manifest; S2 = refresh detection; S3 = consistency; S4 = export blocking.
3. **Split by capability lifecycle**: S1 creates the manifest; S2 monitors changes; S3 ensures consistency; S4 enforces policy.
4. **Closure story**: S4 returns complete dataset validation with enforcement.

### Bad Splits (Avoid)

- "Refresh detection" + "Version consistency" as two stories. They are the same capability — the manifest ensures consistency by detecting changes.

### Story Line Format

Story IDs follow `VX.Y.SN`. Each story is independently compilable and testable.
