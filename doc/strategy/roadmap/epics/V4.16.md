# V4.16: Audit Checks and Severity Enforcement

**Labels:** `type/epic`, `type/feature`, `area/investing`, `area/audit`
**GitHub Issue:** TBD

A valuation without audit checks is just a calculation. V4.16 implements Step 10 audit assertions with severity levels (Error, Warn, Info). Any Error blocks rendering a conclusion. The checks validate: terminal growth ≤ risk-free rate; WACC − g ≥ 100bp; currency consistency; single FX date; CRP derived from default spreads (not read raw); geographic coverage; no invented inputs; FCFF reconciliation; terminal value share < 75%; moat spread supported by historical ROIC − WACC spread. The outcome is that every valuation output is accompanied by a complete audit report that tells the analyst whether the valuation is credible, which assumptions are questionable, and which inputs are unsupported.

## Product Intent

Deliver the audit assertion engine: implement Step 10 audit checks with severity levels (Error, Warn, Info), where any Error blocks rendering a conclusion. Validate all methodology constraints (terminal growth ≤ risk-free rate, WACC − g ≥ 100bp, CRP from default spreads, etc.). The outcome is that every valuation comes with an audit report that certifies or flags the credibility of the result.

## Users And Jobs

- [Investment analyst]: See an audit report alongside the valuation, showing which checks passed (Info), which need attention (Warn), and which block the conclusion (Error).
- [Compliance reviewer]: Verify that every audit check is implemented as specified, that Errors block rendering, and that all methodology constraints from architecture.md are covered.
- [Engineer]: Add new audit checks (e.g., "revenue growth ≤ GDP growth") as policy-configurable assertions without modifying existing check logic.
- [Tickoni tile]: Consume `auditValuation(result)` as a callable pivot that returns the ValuationResult with audit assertions attached.

### How Many Stories?

Four stories: framework (S1), methodology constraints (S2), data integrity (S3), and reconciliation + report assembly (S4). The scope is audit checks — foundational but essential for credibility.

### Decomposition Rules

1. **Independent delivery**: Each story produces verifiable audit output.
2. **One capability per story**: S1 = framework; S2 = methodology checks; S3 = data checks; S4 = reconciliation + report.
3. **Split by capability lifecycle**: S1 sets up the severity system; S2–S3 implement checks; S4 assembles the report.
4. **Closure story**: S4 returns the complete audit report with all checks and severity levels.

### Bad Splits (Avoid)

- "Methodology checks" + "Data checks" as two stories. They are the same capability — audit checks — split only by topic.

### Story Line Format

Story IDs follow `VX.Y.SN`. Each story is independently compilable and testable.
