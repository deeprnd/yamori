# V1.2: Unified Backend Router

**Labels:** `type/epic`, `type/feature`, `area/platform`
**GitHub Issue:** TBD

Moves every direct Arrow/GSL invocation behind one stable semantic dispatch layer while preserving all previous numerical results. Registers Arrow compute functions and GSL adapters behind a capability registry that maps each Yamori operation to its backend implementation. Normalizes backend failures into Yamori statuses and prevents C++ Arrow and GSL implementation types from leaking through Yamori's public surface.

## Product Intent

Deliver the unified backend router: a single dispatch layer that routes every Yamori operation to its backend implementation (Arrow Compute, GSL, or custom kernels) while exposing a stable, language-neutral interface. The outcome is that domain code (valuation formulas, ratios, growth models) never depends on Arrow or GSL directly — it calls Yamori's capability registry and gets backend-agnostic results with normalized errors.

## Users And Jobs

- [Engineer]: Call `dispatch(op, inputs)` without knowing whether the backend is Arrow, GSL, or a custom kernel.
- [Compliance reviewer]: Verify that every backend invocation returns Yamori status types, not C++ Arrow or GSL error types.
- [Investment analyst]: See the same numerical results regardless of which backend is selected, ensuring no precision loss from the dispatch layer.
- [Tickoni tile]: Consume `dispatch()` as a callable pivot that abstracts away backend complexity.

## Success Metrics

- Every Arrow and GSL invocation goes through the capability registry — no direct calls from domain code.
- Backend failures normalized into Yamori status types (`!Error`) — no Arrow/GSL types leak through the public surface.
- Capability registry maps each Yamori operation to exactly one backend implementation.
- Switching backends (Arrow → GSL) produces identical numerical results.
- Zero C++ Arrow or GSL implementation types in Yamori's public API.

## Demo Moment

- Command or flow: `tickoni dispatch --list` shows the full capability registry with operation-to-backend mappings.
- Expected result: A table of all registered operations, their backends, and their normalized status types.

## Scope

### In Scope

- Capability registry: maps Yamori operations to backend implementations (Arrow Compute, GSL, custom).
- Arrow compute dispatch: register Arrow Compute functions behind the registry.
- GSL adapter dispatch: register GSL statistical functions behind the registry.
- Error normalization: all backend failures return Yamori `!Error` types — no Arrow/GSL types leak.
- Backend-agnostic API: domain code calls `dispatch(op, inputs)` without knowing the backend.
- Backend selection: runtime or compile-time selection of backend per operation.
- Provenance: every dispatched operation records its backend, inputs, and output.

### Out Of Scope

- Shared-memory representation (V1.3).
- C ABI (V1.4).
- Deterministic execution policy (V1.5).
- Financial formula dependency graph (V1.1).
- Historical metrics computation (V1.2 in later milestone).
- Cost of capital / WACC (V1.3 in later milestone).

### How Many Stories?

Seven stories: registry (S1), Arrow dispatch (S2), GSL dispatch (S3), error normalization (S4), dispatch API (S5), backend selection (S6), and provenance (S7). Each delivers an independently testable layer of the dispatch infrastructure. The scope is narrow (one dispatch layer), so 7 stories reflects the number of distinct dispatch capabilities.

### Decomposition Rules

1. **Independent delivery**: Each story compiles and produces a verifiable artifact (registry, adapter, dispatcher).
2. **One capability per story**: S1 = schema; S2 = Arrow; S3 = GSL; S4 = error handling; S5 = API; S6 = selection; S7 = provenance.
3. **Split by capability lifecycle**: S1–S3 register backends; S4–S5 expose the API; S6–S7 handle selection and audit.
4. **Closure story**: S7 ensures every dispatched operation records provenance — the audit layer.

### Bad Splits (Avoid)

- "Arrow dispatch" + "GSL dispatch" as one story. They are independently registerable backends.
- "Backend-agnostic API" + "Backend selection" as one story. The API surface and selection mechanism are independently testable.

### Story Line Format

Story IDs follow `VX.Y.SN`. Each story is independently compilable and testable.
