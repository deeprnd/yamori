
# V1.2: Reliable Results Engine

**Labels:** `type/epic`, `type/enhancement`, `area/platform`
**GitHub Issue:** #3

Ensures every numerical result is delivered through a single, auditable routing layer that preserves precision, normalizes errors, and guarantees the same input always produces the same output — no matter which computational engine powers the calculation underneath. Users get the confidence that their valuations are computed correctly, traceably, and identically every time.

## Product Intent

Deliver the results engine: a single routing layer that sends every Yamori calculation to its computational backend while guaranteeing stable, auditable results. Users never need to understand or configure which engine (Arrow, GSL, or custom kernel) performs each calculation — Yamori handles the routing, normalizes errors into clear messages, and guarantees that results are reproducible. The outcome is confidence: users trust every number because the system makes precision and reproducibility structural, not aspirational.

## Users And Jobs

- [Investment analyst]: Run any Yamori calculation and get a reliable, traceable result — no hidden precision loss, no backend errors leaking into user-facing messages.
- [Data researcher]: Swap the computational engine behind a calculation and verify the results haven't changed — reproducibility is structural, not coincidental.
- [Portfolio manager]: See clear, actionable error messages when data is missing or malformed, instead of cryptic system errors.
- [Compliance reviewer]: Audit any calculation's provenance — which engine ran it, with what inputs, and what result it produced.

## Success Metrics

- Every numerical result is delivered through a single routing layer — no hidden backends.
- Errors are normalized and actionable — users see "source metric missing" not system error codes.
- Results are reproducible: the same inputs always produce the same output.
- Swapping the underlying engine does not change results.
- Every calculation is auditable: the system records which engine ran it, with what inputs.

## Demo Moment

- Command or flow: `tickoni run --formula ROIC --sources stla-2024` and see a clean result with a provenance trail showing exactly which engine computed it and with what inputs.
- Expected result: A reliable result with clear error handling — if sources are missing, the error is actionable, not cryptic.

## Scope

### In Scope

- Capability registry: maps Yamori operations to backend implementations (Arrow Compute, GSL, custom).
- Arrow compute dispatch: register Arrow Compute functions behind the registry.
- GSL adapter dispatch: register GSL statistical functions behind the registry.
- Error normalization: all backend failures return Yamori `!Error` types — no Arrow/GSL types leak.
- Backend-agnostic API: domain code calls `dispatch(op, inputs)` without knowing the backend.
- Backend selection: runtime or compile-time selection of backend per operation.
- Provenance: every dispatched operation records its backend, inputs, and output.

### Out Of Scope

- Shared-memory representation (V1.3).
- C ABI (V1.4).
- Deterministic execution policy (V1.5).
- Financial formula dependency graph (V1.1).
- Historical metrics computation (M2, V2.1–V2.2).
- Cost of capital / WACC (M2, V2.3).

### How Many Stories?

Seven stories: registry (S1), Arrow dispatch (S2), GSL dispatch (S3), error normalization (S4), dispatch API (S5), backend selection (S6), and provenance (S7). Each delivers an independently testable layer of the dispatch infrastructure. The scope is narrow (one dispatch layer), so 7 stories reflects the number of distinct dispatch capabilities.

### Decomposition Rules

1. **Independent delivery**: Each story compiles and produces a verifiable artifact (registry, adapter, dispatcher).
2. **One capability per story**: S1 = schema; S2 = Arrow; S3 = GSL; S4 = error handling; S5 = API; S6 = selection; S7 = provenance.
3. **Split by capability lifecycle**: S1–S3 register backends; S4–S5 expose the API; S6–S7 handle selection and audit.
4. **Closure story**: S7 ensures every dispatched operation records provenance — the audit layer.

### Bad Splits (Avoid)

- "Arrow dispatch" + "GSL dispatch" as one story. They are independently registerable backends.
- "Backend-agnostic API" + "Backend selection" as one story. The API surface and selection mechanism are independently testable.

### Story Line Format

Story IDs follow `VX.Y.SN`. Each story is independently compilable and testable.
