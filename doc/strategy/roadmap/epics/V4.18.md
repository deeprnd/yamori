# V4.18: Batch Valuation Runner

**Labels:** `type/epic`, `type/feature`, `area/investing`, `area/operations`
**GitHub Issue:** TBD

A single valuation is a tool; a peer-set valuation is a platform. V4.18 executes M1's `runValuation()` pipeline across an entire peer set in a single batch operation. It shares dataset manifest lookups and policy objects across runs to minimize redundant computation. It produces a peer-set valuation table with all M1/M2/M3 outputs for every company, enabling cross-company comparison from a single execution. The outcome is that 50 companies can be valuated in one batch with the same deterministic pipeline, same audit trail, same data provenance — turning the engine from an analyst's calculator into a portfolio-grade research platform.

## Product Intent

Deliver the batch valuation runner: execute `runValuation()` across an entire peer set in a single batch operation, sharing dataset manifest lookups and policy objects to minimize redundant computation. Produce a peer-set valuation table with all M1/M2/M3 outputs for every company. The outcome is a single execution that produces valuations for the entire peer set — consistent, deterministic, auditable — enabling cross-company comparison from a single run.

## Users And Jobs

- [Investment analyst]: Run valuations across an entire peer set in a single batch and receive a valuation table for all companies.
- [Compliance reviewer]: Verify that dataset manifest lookups are shared across runs (no redundant downloads), that all valuations use the same policy framework, and that every company's valuation carries the same audit trail.
- [Engineer]: Extend the batch runner by adding parallel execution (concurrent `runValuation()` calls) as a performance optimization without changing output order.
- [Tickoni tile]: Consume `batchValuate(peer_set)` as a callable pivot that returns a table of valuations for all companies in the peer set.

## Success Metrics

- Batch execution: `runValuation()` called once per company in the peer set.
- Shared dataset manifest lookups and policy objects: no redundant computation.
- Peer-set valuation table: all M1/M2/M3 outputs for every company.
- Deterministic: same peer set + same inputs produces bit-identical results across runs.
- Audit trail: every company's valuation carries the same audit assertions from M3.
- Error handling: companies with failed valuations are reported; other companies' valuations proceed.

## Demo Moment

- Command or flow: `tickoni batch run --peers <peer_set_file> --scenarios bull base bear`
- Expected result: A valuation table with intrinsic values, implied multiples, audit assertions, and scenario distributions for all companies in the peer set.

### How Many Stories?

Four stories: orchestration (S1), output table (S2), determinism + audit (S3), and error handling + provenance (S4). The scope is batch execution — essential for platform-scale comparative analysis.

### Decomposition Rules

1. **Independent delivery**: Each story produces verifiable batch output.
2. **One capability per story**: S1 = orchestration; S2 = output table; S3 = determinism + audit; S4 = error handling.
3. **Split by capability lifecycle**: S1 sets up batch execution; S2 assembles output; S3 verifies determinism; S4 handles errors.
4. **Closure story**: S4 returns the complete batch result with error handling and provenance.

### Bad Splits (Avoid)

- "Batch orchestration" + "Peer-set valuation table" as two stories. Orchestration and output are one capability — the batch runner.

### Story Line Format

Story IDs follow `VX.Y.SN`. Each story is independently compilable and testable.
