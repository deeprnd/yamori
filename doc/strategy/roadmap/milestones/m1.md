# M1: Yamori Runtime — The Trust Infrastructure for Financial Computation

## Description

Financial computation should be trustworthy, reproducible, and composable — not just accurate, but auditable by anyone, anywhere, on any machine. M1 builds the infrastructure that makes this possible: the financial formula dependency graph, unified backend router, shared-memory representation, C ABI, and deterministic execution policy. The runtime doesn't just compute; it proves.

Most financial tools answer "what number?" Yamori answers "why this number, and how do I know it's right?" The logical fix is to build a calculator. The psycho-logic insight is that people don't distrust numbers — they distrust process. A single number feels arbitrary. A number backed by a traceable, deterministic, reproducible process feels defensible. The runtime exists to transform computation into evidence.

```text
trustworthy process + reproducible results → auditable financial computation
```

M1 establishes the Yamori runtime capabilities identified in `positioning-v2.md` as the project's core differentiators. The financial formula dependency graph knows that `IntrinsicValue depends on FCFF depends on EBIT depends on tax...` and can re-evaluate the graph for sensitivity, Monte Carlo, and reverse DCF. The backend router moves every direct Arrow/GSL invocation behind one stable dispatch layer. The shared-memory representation enables zero-copy cross-process data sharing. The C ABI freezes a language-neutral interface for research→production parity. The deterministic execution policy pins algorithms, RNG, threading, and reduction order. No domain logic ships until this foundation exists — because trust must be built before value is claimed.

## Library Dependencies

**Library: Apache Arrow C++ (core, CSV, Compute, C Data Interface)** — Canonical memory representation, CSV I/O, compute registry, and language-neutral interchange.

**Not used: GSL, Cuba, QuantLib, BLAS/LAPACK, TA-Lib, FFTW, nanoarrow.** M1 uses Arrow only. GSL enters in M2 for statistics/interpolation/roots. Cuba, QuantLib, BLAS/LAPACK, TA-Lib, FFTW are post-M4 additions. nanoarrow enters in M4 for the C ABI layer.

## Included Epics

### Epic V1.1 — Financial formula dependency graph

Defines financial metrics as named dependency graphs over source metrics; derived metrics resolve in deterministic topological order without performing numerical work themselves. The graph enables sensitivity analysis, Monte Carlo simulation, and reverse DCF because `runValuation()` traverses the graph rather than calling a monolithic function. Named formulas describe a derived metric by name, required source metrics, and backend operations. This is Yamori's strongest differentiator: the graph, not any single formula, is the reusable asset.

### Epic V1.2 — Unified backend router

Moves every direct Arrow/GSL invocation behind one stable semantic dispatch layer while preserving all previous numerical results. Registers Arrow compute functions and GSL adapters behind a capability registry that maps each Yamori operation to its backend implementation. Normalizes backend failures into Yamori statuses and prevents C++ Arrow and GSL implementation types from leaking through Yamori's public surface.

### Epic V1.3 — Shared-memory representation

Allows the same financial arrays and tables to be mapped by multiple processes while retaining Arrow-compatible layout. Establishes Arrow's C Data Interface as the interoperability substrate, wraps owned/borrowed/foreign buffers, and implements offset-based buffer descriptors so shared memory references workspace-relative offsets rather than process-local pointers. Enables zero-copy process attach for cross-process data sharing.

### Epic V1.4 — C ABI

Freezes a language-neutral interface that exposes the proven runtime capabilities through C-callable functions. Uses Arrow's C Data Interface structures for array/table interchange, exposes normalized backend status/error information as stable C types, and provides opaque handles for backend state such as solvers or RNGs. ABI compatibility tests detect accidental binary-interface breakage across releases.

### Epic V1.5 — Deterministic execution policy

Implements the deterministic execution framework identified in `positioning-v2.md` as "one of the hardest claims Yamori could make." Pins algorithms, pins RNG with explicit seed, enforces deterministic threading policy, specifies reduction order, and disables fast-math. Produces bit-identical results across Linux x86, Linux ARM, macOS ARM, and Windows x86. This is not a collection of tests — it is a built capability that every downstream milestone depends on.

## Why This Is A Milestone

M1 transforms Yamori from a domain-specific calculator into a composable financial computation runtime — but more importantly, it transforms financial computation from a black box into a transparent, auditable process. Every other milestone depends on the dependency graph (which makes sensitivity/Monte Carlo possible), the backend router (which isolates domain code from backend changes), the shared-memory representation (which enables multi-process pipelines), the C ABI (which enables research→production parity), and the deterministic execution policy (which makes outputs auditable).

The epics build these runtime capabilities first, then prove them with domains — the correct sequence identified by the product strategy. This is not a refactor; it is the first domain-independent capability that Yamori delivers. The runtime exists before any domain logic ships because trust infrastructure is the first thing people need, not the last thing they check.

## Completion Signal

The financial formula dependency graph resolves derived metrics in deterministic topological order. The backend router dispatches every operation through the capability registry. Shared-memory buffers are zero-copy accessible across processes. The C ABI exposes all runtime capabilities with ABI compatibility tests passing. The C ABI is consumable from Python for research→production parity validation.
