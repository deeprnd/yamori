# V1.5.S2: RNG pinning — explicit seed for all random operations

**Labels:** `type/story`, `area/platform`, `type/feature`
**GitHub Issue:** #90

Eliminate all implicit entropy sources. Every random operation in Yamori requires an explicit seed, and the RNG state is fully deterministic given that seed.

## Product Outcome

No random operation in Yamori draws from system entropy. Every RNG call is seeded explicitly by the caller, and the resulting sequence is reproducible — bit-for-bit — across all platforms.

## User Story

As a compliance reviewer, I want every random number generated by Yamori to be traceable to an explicit seed, so that I can reproduce any Monte Carlo or stochastic computation from the same starting point.

## Scope

- In scope: identify all RNG call sites, replace implicit sources (OS entropy, `std.crypto.random`) with seed-based RNG, add a seeded RNG type to the runtime, enforce seed requirement at API boundaries.
- Out of scope: algorithm pinning (S1), threading policy (S3), reduction order (S4), fast-math (S5), harness (S6), provenance (S7).

## Preconditions And Assumptions

- V1.5.S1 (algorithm pinning) provides the base determinism framework; S2 builds on top of it.
- Yamori currently uses standard library random sources in at least some paths (e.g., sampling, shuffling).
- A seeded RNG type (e.g., PCG, Xoshiro) is available in the runtime or must be added.

## Acceptance Criteria

- [ ] Given an explicit seed, when a stochastic operation (Monte Carlo, sampling, shuffling) runs, then the output is deterministic on all four target platforms.
- [ ] Given a call to any Yamori API that internally uses randomness, when no seed is provided, then the call returns `Error` (fail-closed: no implicit entropy).
- [ ] All direct calls to `std.crypto.random` and other implicit entropy sources are removed from the Tickoni codebase.
- [ ] The seeded RNG state is a first-class type in the runtime, passed explicitly through the call chain.

## Notes And Open Questions

- Which seeded RNG algorithm to use? PCG is recommended for its speed, small state (128 bits), and excellent statistical properties. Xoshiro256** is a simpler alternative.
- Should the seed be passed per-call or maintained as a thread-local RNG instance? Per-call is simpler but may not support sequential generation; thread-local is more efficient but introduces scope concerns.
