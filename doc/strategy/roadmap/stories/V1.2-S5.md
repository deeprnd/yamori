# V1.2.S5: Backend-agnostic dispatch API — domain code calls dispatch(op, inputs) without knowing the backend

**Labels:** `type/story`, `area/platform`, `type/feature`
**GitHub Issue:** #73

Implement the `dispatch(op, inputs)` function: the backend-agnostic API that domain code calls to execute any registered operation. Domain code does not know or care which backend (Arrow, GSL, custom) powers the computation — it calls `dispatch` with an operation name and inputs, and the dispatch layer routes to the correct backend through the capability registry.

## Product Outcome

Domain code can compute any registered operation by calling a single function: `dispatch(op, inputs) -> Result | !Error`. The domain layer is decoupled from backend selection — swapping Arrow for GSL or adding a new backend requires zero changes to domain code. This is the callable pivot of the results engine: every computation flows through `dispatch()`.

## User Story

As an investment analyst, I want to run any Yamori calculation by calling a single dispatch function so that I don't need to know or care which backend is powering the computation.

## Scope

- In scope: `dispatch(op_name, inputs) -> Result | !Error` function. Registry lookup: `dispatch` calls `registry.lookup(op_name)` to find registered backend(s). Backend invocation: `dispatch` calls the appropriate backend adapter's `dispatch` method with normalized inputs. Error handling: `dispatch` returns `!Error` via S4 normalization. Input validation: `dispatch` validates inputs before routing (type checks, non-empty). Return the result to the caller. Integration test: domain code calls `dispatch("mean", array)` and gets a result without importing Arrow or GSL directly.
- Out of scope: Backend selection strategy (S6). Provenance recording (S7). Arrow dispatch registration (S2). GSL dispatch registration (S3). Error normalization (S4).

## Preconditions And Assumptions

- S1 (capability registry) is implemented and provides add/lookup/list/remove operations.
- S2 (Arrow adapter) and S3 (GSL adapter) are implemented and can dispatch operations.
- S4 (error normalization) is implemented and converts all backend errors to `!Error`.
- The `dispatch` function is the public API entry point; domain code calls it, not individual adapters.

## Acceptance Criteria

- [ ] Given a registered operation is dispatched via `dispatch(op_name, inputs)`, when the registry finds a registered backend, then the backend's dispatch method is called with normalized inputs and the result is returned.
- [ ] Given an unregistered operation is dispatched, when `dispatch` calls the registry lookup, then it returns `!Error(NotRegistered)` without calling any backend adapter.
- [ ] Given multiple backends are registered for the same operation, when `dispatch` is called, then it uses the default backend (highest priority or first registered) without the caller specifying which one.
- [ ] Given an operation fails inside a backend, when the backend returns an error, then `dispatch` normalizes it via S4 and returns `!Error` to the caller.
- [ ] Given domain code calls `dispatch("mean", input_array)`, when the result is returned, then domain code did not import Arrow or GSL directly — the backend is transparent.
- [ ] Given invalid inputs (empty array, wrong type), when `dispatch` validates inputs before routing, then it returns `!Error(InvalidInput)` before any backend is called.

## Notes And Open Questions

- Should `dispatch` accept inputs as a generic struct/map or as typed arrays? (Decision: generic struct/map for flexibility; typed adapters handle conversion internally.)
- Should `dispatch` support async execution for slow operations? (Decision: no for V1.2; synchronous dispatch only. Async is M2+.)
- Should `dispatch` accept a backend hint parameter to override the default? (Decision: no — backend selection is S6. For V1.2, `dispatch` uses the registry's default priority.)
