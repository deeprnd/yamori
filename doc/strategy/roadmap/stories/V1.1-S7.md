# V1.1.S7: Provenance — every computed metric carries dependency chain and formula definition

**Labels:** `type/story`, `area/platform`, `type/feature`
**GitHub Issue:** #68

Attach provenance metadata to every computed metric: the full dependency chain, the formula definition, and the source references. This enables traceability from any computed number back to raw financial data.

## Product Outcome

Every computed metric carries its full chain of composition — a user can inspect any number and see exactly which source metrics and operations produced it. This traceability is Yamori's core differentiator: every result is auditable from the final number back to the raw data.

## User Story

As an investment analyst, I want to trace any computed metric back through its composition chain to the raw financial data, so that I can verify every step of the calculation and audit the result.

## User Story

As a data researcher, I want every computed metric to carry its formula definition and dependency chain, so that I can audit how any result was produced without inspecting the code.

## Scope

- In scope: Provenance metadata struct (formula name, source metrics list, operation, dependency chain as ordered list of formula names). Attach provenance to results in `runValuation()` (S5) and re-evaluation (S6). Query provenance: given a formula name, return its provenance chain. Include provenance in the output of the demo command.
- Out of scope: Audit record persistence (V5). Replay (V5). User-facing audit UI (V5).

## Preconditions And Assumptions

- Formula definitions (S1) contain the name, source metrics, and operation.
- Dependency resolution (S2) produces the ordered computation sequence.
- Provenance is computed at the same time as the formula result (no separate traversal needed).

## Acceptance Criteria

- [ ] Given a formula ROIC = NOPAT / InvestedCapital, when the formula is computed, then the result carries provenance: {name: "ROIC", sources: ["NOPAT", "InvestedCapital"], operation: "divide", chain: ["NOPAT", "InvestedCapital", "ROIC"]}.
- [ ] Given a chain of formulas A→B→C, when C is computed, then its provenance chain includes all ancestors: [A, B, C].
- [ ] Given a computed result, when provenance is queried by formula name, then the full chain and definition are returned.
- [ ] Given a leaf metric (no sources), when provenance is queried, then the chain is [metric_name] (single element, no operations).
- [ ] Given a formula that was re-evaluated (S6), when provenance is queried, then the chain is the same as before (provenance does not change on re-evaluation).

## Notes And Open Questions

- Should the provenance chain be stored as a flat list (all ancestors) or as a tree structure? (Decision: flat list for simplicity; tree structure can be added later for complex multi-branch compositions.)
