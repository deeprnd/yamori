# V1.3.S6: Buffer provenance — source process, offset, and lifetime tracking for every shared buffer

**Labels:** `type/story`, `area/platform`, `type/feature`
**GitHub Issue:** #81

Implement buffer provenance: every shared buffer records its source process, byte offset, creation timestamp, and lifetime metadata. This provides an auditable trail for every data segment that flows through the shared memory layer, enabling compliance reviewers and operators to verify the origin and lifecycle of shared data.

## Product Outcome

Every shared buffer in Yamori carries a complete provenance record: which process created it, at what offset in the shared segment, when it was created, and how long it has been active. This transforms shared memory from an opaque optimization into an auditable exchange layer. Compliance reviewers can verify that every data segment has a known source and valid lifetime, and operators can diagnose stale or orphaned buffers.

## User Story

As a compliance reviewer, I want every shared data segment to carry a provenance record showing its source process, offset, and lifetime so that I can verify the data flows through Yamori with full traceability.

## Scope

- In scope: Provenance record type — fields: source process ID, segment ID, byte offset, creation timestamp, lifetime duration (seconds since creation), status (active/expired/revoked). Provenance attachment: every buffer created or attached via S4/S5 carries its provenance record. Provenance lookup: query provenance by segment ID or source process. Provenance validation: verify a buffer's provenance is current (not expired, not revoked). Error returns for expired provenance, revoked buffers, or missing provenance records.
- Out of scope: Arrow C Data Interface (S1 — already complete). Buffer wrappers (S2 — already complete). Offset descriptors (S3 — already complete). Zero-copy attach (S4 — already complete). Shared memory creation (S5 — already complete).

## Preconditions And Assumptions

- Shared segments are created and tracked by S5.
- Buffer attach/detach operations are tracked by S4.
- Provenance records are in-memory only; persistent audit logging is deferred to V5.
- Source process ID is a stable integer or string identifier assigned at process startup.
- Timestamps use a monotonic clock (not wall clock) to avoid issues with clock adjustments.

## Acceptance Criteria

- [ ] Given a shared buffer created or attached, when its provenance is recorded, then the source process ID, segment ID, byte offset, creation timestamp, and status are stored.
- [ ] Given a provenance record, when queried by segment ID, then the correct source process, offset, and status are returned.
- [ ] Given a provenance record with a timestamp exceeding the maximum lifetime, when validated, then the record returns Error (provenance expired).
- [ ] Given a provenance record that has been revoked, when the associated buffer is accessed, then the operation returns Error (provenance revoked).
- [ ] Given a buffer with no provenance record, when accessed, then the operation returns Error (unverified buffer).

### Conditional Acceptance

**Financial capability and policy**

- [ ] N/A - buffer provenance is an audit trail mechanism, not a financial capability or policy mechanism.

**Audit and replay**

- [ ] Applies - every shared buffer carries a provenance record that forms the audit trail for data exchange. Provenance records are append-only: status transitions are active → expired or active → revoked; records are never deleted.

**Runtime topology and tile ownership**

- [ ] N/A - provenance is a metadata layer, not a topology change. All tiles that can access a segment can query its provenance.

**Model, tool, adapter, or execution boundary**

- [ ] N/A - no model or adapter calls. The provenance layer is a metadata registry.

**CaseOps API or UI**

- [ ] N/A - no API or UI contract changes.

**Security and fail-closed behavior**

- [ ] Applies - access to buffers without valid provenance must return Error, never silently proceed. Revoked provenance must prevent all access.

## Notes And Open Questions

- Should the maximum lifetime be a fixed value (e.g., 3600 seconds) or per-buffer? (Decision: per-buffer — the attaching process specifies the maximum lifetime when attaching.)
- Should provenance records be persisted to disk (audit log) or kept in-memory only? (Decision: in-memory only for V1.3; persistent audit logging is V5.)
- How should provenance handle buffer migration between processes? (Decision: provenance records the original source; migration creates a new provenance entry for the transferring process. The record chain forms a provenance path.)
