# V1.3.S2: Buffer wrappers — owned, borrowed, and foreign buffer types with distinct semantics

**Labels:** `type/story`, `area/platform`, `type/feature`
**GitHub Issue:** TBD

Define buffer wrapper types with distinct ownership semantics: owned (the buffer owns its underlying memory), borrowed (the buffer references memory managed elsewhere with a lifetime guarantee), and foreign (the buffer wraps memory from an external process with no local ownership). These wrappers enforce correct lifetime discipline at the type system level.

## Product Outcome

All shared memory buffers in Yamori carry explicit ownership semantics encoded in their type. No buffer can accidentally outlive its source, and no process can mutate memory it does not own. This eliminates the class of bugs where shared buffers are freed prematurely, double-freed, or corrupted by unauthorized writes.

## User Story

As a portfolio manager, I want every buffer I share between processes to carry explicit ownership semantics so that I never accidentally free memory that another process depends on.

## Scope

- In scope: Buffer wrapper types — `OwnedBuffer`, `BorrowedBuffer`, `ForeignBuffer` with distinct struct layouts. Ownership transfer semantics: owned buffers manage their own memory lifecycle; borrowed buffers carry a lifetime marker and cannot be freed; foreign buffers wrap external memory with read/write permission flags. Buffer metadata: base pointer, length, capacity, permission (read/write/readonly). Error returns on ownership violations (e.g., freeing a borrowed buffer, mutating a readonly foreign buffer).
- Out of scope: Offset-based descriptors (S3). Zero-copy attach (S4). Shared memory creation (S5). Provenance tracking (S6).

## Preconditions And Assumptions

- No buffer wrapper types exist in the codebase.
- The Arrow C Data Interface (S1) defines the interchange layout that buffers will wrap.
- Memory allocation and deallocation are handled by the underlying system; wrappers manage lifetime discipline only.
- Foreign buffers assume the external process guarantees the memory remains valid for the lifetime of the foreign reference.

## Acceptance Criteria

- [ ] Given an owned buffer, when it is created, then it allocates and manages its own memory; when freed, the memory is released.
- [ ] Given a borrowed buffer referencing an owned buffer, when the borrowed buffer is destroyed, then the underlying memory is NOT released (ownership remains with the owned buffer).
- [ ] Given a foreign buffer wrapping external memory with readonly permission, when the buffer is mutated, then the operation returns Error (permission denied).
- [ ] Given an attempt to free a borrowed buffer, when the free operation is invoked, then the operation returns Error (cannot free borrowed memory).
- [ ] Given a buffer with zero length, when accessed, then the operation returns Error (empty buffer).

## Notes And Open Questions

- Should buffer wrappers use Zig's `comptime` to enforce lifetime at compile time, or rely on runtime checks? (Decision: runtime checks for cross-process safety; comptime enforcement where possible for local buffers.)
- How do foreign buffers handle memory that the external process frees while a foreign reference is still active? (Decision: this is a programmer error; the foreign buffer carries a validity token that must be checked before access — validation deferred to S5/S6.)
- Should the buffer wrapper include a reference count for shared ownership? (Decision: no — explicit borrow/foreign semantics replace implicit refcounting; S4 handles attach semantics.)
