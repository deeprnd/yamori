# V1.4.S2: Arrow C Data Interface — zero-copy array and table interchange via ArrowSchema and ArrowArray

**Labels:** `type/story`, `area/platform`, `type/feature`
**GitHub Issue:** #83

Define the Arrow C Data Interface functions that enable zero-copy array and table interchange between Yamori's C ABI and external consumers. Arrays and tables flow across language boundaries as `ArrowSchema` and `ArrowArray` structs — no serialization, no copying, no format translation.

## Product Outcome

Yamori exposes its computational results as Arrow C Data arrays and tables that any language can read directly. A Python consumer reads a float64 array from a pricing result without copying bytes; a Rust consumer iterates over a table of risk metrics without deserialization. The data stays where it lives and the consumer reads it in place.

## User Story

As a data researcher, I want Yamori's output arrays and tables available as Arrow C Data structs so that I can read computational results in-place without serialization or copying, regardless of what language I'm using.

## Scope

- In scope: Arrow C Data Interface functions exposed through the C ABI (e.g., `yamo_array_to_arrow`, `yamo_table_to_arrow`). Support for `ArrowSchema` (type description, name, children) and `ArrowArray` (null count, length, null bitmap, buffers). Buffer layout: pointers to contiguous memory, byte offsets, data type strings. Validation: struct layout sanity checks (non-null required fields, consistent lengths, valid type strings). Error returns for malformed inputs. Support for top-level arrays and tables with named child arrays.
- Out of scope: Buffer ownership and lifetime management (S4). Offset-based descriptors (deferred). Shared memory attachment across processes (V5). Buffer provenance and audit trails (V5).

## Preconditions And Assum assumptions

- The Arrow C Data Interface types (`ArrowSchema`, `ArrowArray`) are available as C-compatible structs (standard Apache Arrow C Data spec).
- Yamori's internal data structures can be represented as contiguous memory buffers with known data types.
- The C wrapper layer (S1) is stable and provides function declaration patterns.

## Acceptance Criteria

- [ ] Given a valid Yamori internal array (contiguous buffers, known data type), when converted to Arrow C Data, then the resulting `ArrowArray` struct has correct length, null count, and buffer pointers.
- [ ] Given a valid Yamori internal table (list of named arrays), when converted to Arrow C Data, then the resulting `ArrowArray` struct has correct child count and each child's name matches.
- [ ] Given an `ArrowSchema` with a valid type string, when validated, then the validation returns `YAMO_OK`.
- [ ] Given an `ArrowArray` with null buffer pointers for required fields, when validated, then the validation returns `YAMO_ERR_INVALID_INPUT`.
- [ ] Given a zero-length array, when converted to Arrow C Data, then the resulting struct reports length zero and null buffers.

## Notes And Open Questions

- Which Arrow data types map to which Yamori internal types? (Decision: float64 → "d", int32 → "i", int64 → "l", bool → "g", string → "u" (utf8); follow the Arrow C Data spec for type strings.)
- Who owns the Arrow buffer memory after conversion? (Decision: Yamori owns the buffers; the consumer reads them until the next call. Lifetime management is S4.)
- Should the Arrow C Data Interface include nested array types (e.g., struct arrays)? (Decision: top-level arrays and named child arrays only for V1.4; nested types are deferred.)
