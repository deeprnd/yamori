# V1.3.S1: Arrow C Data Interface — establish as the interoperability substrate for array and table interchange

**Labels:** `type/story`, `area/platform`, `type/feature`
**GitHub Issue:** TBD

Define the Arrow C Data Interface as Yamori's standard for zero-copy array and table interchange between computational components. This interface provides a language-agnostic, pointer-free layout contract that all shared-memory buffers will follow, enabling any component to describe and consume data without serialization or copying.

## Product Outcome

The Arrow C Data Interface becomes the single interchange contract for all data moving between Yamori's computational components. Every array and table exchanged between processes carries a standard, self-describing layout that any consumer can interpret without copying or serializing. This eliminates the serialization bottleneck that traditionally forces users to choose between computational depth and speed.

## User Story

As a data researcher, I want every dataset exchanged between processes to follow a standard, self-describing layout so that I never need to export, serialize, or reformat data to feed it into another process.

## Scope

- In scope: Arrow C Data Interface structs (`ArrowSchema`, `ArrowArray`) as the interchange layout. Array metadata: type, null count, length, null bitmap. Buffer descriptors: pointers to underlying buffers with byte offsets. Table layout: list of arrays with names. Validation: layout sanity checks (non-null pointers, consistent lengths, valid type strings). Error returns for malformed layouts. `tickoni data describe` CLI scaffolding for inspecting Arrow C Data layouts.
- Out of scope: Buffer ownership semantics (S2). Offset-based descriptors (S3). Zero-copy attach across processes (S4). Shared memory creation (S5). Provenance tracking (S6).

## Preconditions And Assumptions

- No Arrow C Data Interface implementation exists in the codebase.
- The interface must be compatible with the Apache Arrow C Data Interface specification (C ABI stable structs).
- All shared buffers must follow this layout; components producing data are responsible for populating it correctly.
- Validation is structural only; semantic validation of data values is deferred.

## Acceptance Criteria

- [ ] Given valid Arrow C Data structs (non-null pointers, consistent lengths, valid type string), when a layout is inspected, then the type, length, null count, and buffer count are reported correctly.
- [ ] Given an Arrow C Data struct with null pointers for required fields, when inspected, then the function returns Error (invalid layout).
- [ ] Given an Arrow C Data array with mismatched child array lengths, when inspected, then the function returns Error (inconsistent layout).
- [ ] Given a table layout with named arrays, when the table is described, then each array's name and metadata are reported.
- [ ] Given a table with zero arrays, when described, then an empty table layout is returned.

## Notes And Open Questions

- Should the Arrow C Data Interface be implemented as a pure C-compatible layer or as a Zig wrapper over C FFI? (Decision: Zig wrapper over C FFI to maintain ABI compatibility; S2–S5 build on this layer.)
- How do Arrow type strings map to Yamori's internal type system? (Decision: defer type mapping; this story focuses on layout validity, not semantic type resolution.)
- Should the `ArrowSchema` include a parent reference for nested types? (Decision: yes, follow the Arrow C Data spec exactly; parent is null for top-level arrays.)
