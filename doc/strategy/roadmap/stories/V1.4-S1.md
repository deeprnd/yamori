# V1.4.S1: C function declarations — expose all runtime capabilities as C-callable functions

**Labels:** `type/story`, `area/platform`, `type/feature`
**GitHub Issue:** #82

Define the C function declarations that form the universal access surface: every runtime capability exposed through stable `extern "C"` wrapper functions with consistent calling conventions and signature patterns. This is the foundational layer — the callable pivot between Yamori's C++ internals and any external consumer.

## Product Outcome

Every computational capability in Yamori becomes callable from any language through a stable C function signature. A Rust program, a Python script, or a Go service all call the same function names with the same parameter layouts, producing identical outputs. No C++ compilation, no header dependencies — just a clean C interface.

## User Story

As a software engineer, I want every Yamori capability callable through stable C function signatures so that I can consume it from any language without C++ compilation or build system configuration.

## Scope

- In scope: `extern "C"` wrapper functions for all runtime capabilities (valuation, pricing, risk metrics). Consistent calling convention: `yamo_<capability>_<action>` naming (e.g., `yamo_valuation_run`, `yamo_pricing_compute`). Function signature pattern: input struct pointer, output struct pointer, status code return. Header file: `yamori_c.h` with `#ifndef` guards, include guards, and stable symbol exports. Linkage: C-compatible library (`.a`/`.so`) that links without C++ stdlib in the consumer's link line.
- Out of scope: Arrow C Data interface (S2). Error types (S3). Opaque handles (S4). ABI tests (S5). Python binding (S6). Documentation (S7).

## Preconditions And Assumptions

- The runtime capabilities exist behind the C++ boundary (delivered by V1.1–V1.3).
- Each capability has a single entry point that can be wrapped by an `extern "C"` function.
- The C++ implementation does not throw exceptions across the C boundary — all error paths return status codes.
- The header file `yamori_c.h` is the sole public interface; consumers include only this header.

## Acceptance Criteria

- [ ] Given a runtime capability (e.g., valuation), when its C wrapper function is called with valid input, then it delegates to the C++ implementation and returns the computed output with status `YAMO_OK`.
- [ ] Given a C wrapper function, when called with a null input pointer, then it returns `YAMO_ERR_INVALID_INPUT` without dereferencing.
- [ ] Given the header file `yamori_c.h`, when included from a C source file, then it compiles without C++ extensions or exceptions.
- [ ] Given the compiled C library, when linked from a C consumer, then the consumer's binary does not depend on libstdc++ or any C++ runtime.
- [ ] Given all declared C functions, when queried via `nm`, then every symbol has a plain C name (no C++ mangled names).

## Notes And Open Questions

- Should the C header use fixed-width types (`int32_t`, `uint64_t`) or C++ types? (Decision: fixed-width types for ABI stability across compilers and platforms.)
- What is the error convention: return status code with output struct via pointer, or return status code with result in output struct? (Decision: status code return + output struct pointer, consistent with the Arrow C Data pattern from V1.3.)
- Should wrapper functions accept input by value or by pointer? (Decision: by pointer — allows null validation and supports large structs without copying.)
