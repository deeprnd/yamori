# V1.4.S5: ABI compatibility tests — detect accidental binary-interface breakage across releases

**Labels:** `type/story`, `area/platform`, `type/feature`
**GitHub Issue:** #86

Define and implement ABI compatibility tests that detect accidental breakage of the C binary interface between releases. These tests act as an automated gate: if any ABI function's signature, struct layout, or symbol export changes, the test fails and blocks the release.

## Product Outcome

Every C ABI function, struct layout, and symbol export is verified for binary compatibility. If a developer accidentally changes a struct's field order, renames a function, or alters an enum value, the ABI test suite catches it before release. This ensures that a binary built against `yamori_c.h` from release N continues to work with the library from release N+1.

## User Story

As a Rust developer, I want ABI compatibility tests that catch accidental changes to the C interface so that my compiled code never silently breaks when I upgrade to a new Yamori release.

## Scope

- In scope: Struct layout tests: verify `@sizeOf` and `@alignOf` of every ABI-exposed struct matches the expected layout. Enum value tests: verify every `YamoStatus` value has a known, stable integer representation. Symbol export tests: verify every expected function symbol is exported with the correct name (no mangling). Header inclusion tests: verify the header compiles cleanly from C (no C++ extensions). Golden ABI file: a reference binary interface dump that the test suite compares against. Test harness: a dedicated test binary that runs all ABI checks.
- Out of scope: Cross-version binary compatibility testing (deferred to release process). ABI migration tools (deferred). ABI versioning scheme (deferred).

## Preconditions And Assumptions

- The C ABI surface (functions, structs, enums) from S1–S4 is stable enough to define a reference layout.
- The build system can compile a test binary that includes the C ABI header and runs struct/introspection tests.
- The test binary runs on the same platform as the target ABI.

## Acceptance Criteria

- [ ] Given the ABI header `yamori_c.h`, when compiled from a C source file, then it produces zero warnings and zero errors.
- [ ] Given every ABI-exposed struct, when its `@sizeOf` and `@alignOf` are computed, then they match the expected golden values.
- [ ] Given every `YamoStatus` enum value, when queried, then it has a stable, documented integer representation.
- [ ] Given the compiled C library, when queried via `nm`, then every expected function symbol is present with a plain C name (no C++ mangling).
- [ ] Given a modified ABI header (e.g., reordering a struct field), when the ABI tests run, then the test suite fails with a clear message identifying the changed element.

## Notes And Open Questions

- How do we handle struct padding and alignment across different compilers? (Decision: test on the target platform (Linux x86_64) and accept platform-specific golden values; cross-platform ABI stability is verified by the CI build matrix.)
- Should the golden ABI file be committed to the repo or generated at test time? (Decision: committed to the repo so test failures are immediately visible in diffs; regenerate and commit when a deliberate ABI change is approved.)
- What happens if the ABI test fails on a feature branch but the ABI is intentionally being redesigned? (Decision: the ABI test is a release gate, not a branch gate. Intentional ABI changes require a documented ABI bump and regenerated golden file.)
