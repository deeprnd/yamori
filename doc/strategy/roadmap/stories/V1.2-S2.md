# V1.2.S2: Arrow compute dispatch — register Arrow Compute functions behind the capability registry

**Labels:** `type/story`, `area/platform`, `type/feature`
**GitHub Issue:** #70

Register Arrow Compute functions behind the capability registry established in S1. This maps Arrow Compute operation names (e.g., "divide", "multiply", "subtract", "add", "sum", "mean") to the Yamori operation namespace, enabling Arrow to execute any registered operation through the dispatch layer.

## Product Outcome

Arrow Compute functions become available as backends for the capability registry. Domain code can request any Arrow-supported operation and get a result through the normalized dispatch API, without knowing it's using Arrow under the hood. This is the first concrete backend wired into Yamori's results engine.

## User Story

As a data researcher, I want to register Arrow Compute functions as a backend in Yamori so that existing Arrow operations can power calculations without code changes in the domain layer.

## Scope

- In scope: Arrow adapter module that wraps Arrow Compute calls. Registration of Arrow-backed operations into the capability registry (S1). Mapping of Arrow Compute function names to Yamori operation names. Input normalization: convert Yamori input types to Arrow-compatible types (arrays, scalars). Error capture: convert Arrow errors to Yamori `!Error` types (deferred normalization, S4). Dispatch test: register an Arrow operation, dispatch through S1 registry, verify result.
- Out of scope: GSL dispatch (S3). Error normalization (S4). Backend selection logic (S6). Provenance recording (S7). Arrow array data source (V1.3).

## Preconditions And Assumptions

- The capability registry (S1) is implemented and provides add/lookup/list/remove operations.
- Arrow Compute is available as a dependency; the adapter will link against the Arrow C Data Interface.
- Arrow Compute function names serve as the canonical operation identifiers (e.g., "divide" → `arrow::compute::divide`).
- Arrow errors are captured by the adapter and will be normalized in S4.

## Acceptance Criteria

- [ ] Given the Arrow adapter, when `register_arrow_backends(registry)` is called, then all supported Arrow Compute operations are registered in the capability registry with backend identifier "arrow".
- [ ] Given an Arrow-backed operation is registered, when dispatch is invoked through the registry with that operation name, then the Arrow Compute function is called with normalized inputs and a result is returned.
- [ ] Given an Arrow operation is dispatched with valid inputs, when the result is returned, then it matches the expected Arrow Compute output (verified by golden test).
- [ ] Given an Arrow operation is dispatched with invalid inputs, when the Arrow Compute call fails, then the error is captured and returned as a Yamori `!Error` type (not a raw Arrow error).
- [ ] Given multiple Arrow operations are registered (divide, multiply, add, subtract), when each is dispatched independently, then each produces the correct result for a standard test case.

## Notes And Open Questions

- Which Arrow Compute functions are in scope for V1.2? (Decision: basic arithmetic operations only — add, subtract, multiply, divide, sum, mean. Additional ops added per domain need.)
- Should the Arrow adapter handle data source conversion (e.g., CSV → Arrow arrays)? (Decision: no. Data source conversion is V1.3. The adapter receives pre-converted Arrow arrays from the caller.)
- Should the adapter support Arrow's batch processing or operate on single arrays only? (Decision: single arrays for V1.2; batch processing is M2+.)
