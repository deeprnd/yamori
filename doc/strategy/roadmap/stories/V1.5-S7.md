# V1.5.S7: Determinism provenance — seed, thread count, reduction order in every result

**Labels:** `type/story`, `area/audit`, `type/feature`
**GitHub Issue:** #95

Every deterministic result records its provenance: the seed used, the thread count, and the reduction order. Operators can trace any number back to the exact conditions under which it was computed.

## Product Outcome

Every numerical result produced by Yamori carries a provenance envelope containing the seed, thread count, and reduction order. This is the audit layer that makes determinism traceable — not just reproducible, but auditable.

## User Story

As a compliance reviewer, I want every number in a Yamori output to be traceable to its seed, thread count, and reduction order, so that I can verify that the computation was deterministic and reproducible.

## User Story

As a portfolio manager, I want to share a valuation with a colleague and include its provenance, so that they can reproduce the exact result on their own platform.

## Scope

- In scope: define a provenance envelope type (seed, thread_count, reduction_order, algorithm_id, hash), attach provenance to every deterministic result, add provenance to the output format, verify provenance completeness via the harness (S6).
- Out of scope: algorithm pinning (S1), RNG pinning (S2), threading policy (S3), reduction order (S4), fast-math (S5), harness (S6).

## Preconditions And Assumptions

- V1.5.S1–S6 must be complete before S7 can attach meaningful provenance to results.
- The output format (JSON, CSV, or custom) must support embedded provenance metadata.
- The harness (S6) should validate provenance completeness as part of its verification.

## Acceptance Criteria

- [ ] Given a deterministic computation, when the result is produced, then the output includes a provenance envelope with seed, thread count, reduction order, and algorithm ID.
- [ ] Given a result with incomplete provenance (missing seed, thread count, or reduction order), when the result is validated, then the validation fails with a descriptive error.
- [ ] Given a provenance envelope and the same input data, when a user reproduces the computation with those provenance values, then the output hash matches the original (via the harness from S6).
- [ ] Given an invalid seed, thread count, or reduction order in the provenance envelope, when a computation is attempted, then the call returns `Error`.

## Notes And Open Questions

- Should the provenance envelope include a computed hash of the result (so that any tampering is detectable), or should it only record the input conditions? Including a result hash is stronger (detects tampering) but requires the harness (S6) to be in place.
- What format for the provenance envelope? JSON is human-readable but adds serialization complexity. A binary format is compact but harder to inspect. Given that Yamori's outputs are typically JSON, JSON provenance is the natural choice.
