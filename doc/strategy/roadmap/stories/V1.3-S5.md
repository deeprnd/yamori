# V1.3.S5: Shared memory creation and mapping — create segments, map in multiple processes

**Labels:** `type/story`, `area/platform`, `type/feature`
**GitHub Issue:** #80

Implement the shared memory layer: create shared segments, allocate byte capacity, and provide platform-specific creation and mapping. This is the foundation that S4's zero-copy attach builds on — without shared segments, there is nothing to attach.

## Product Outcome

Processes can create named shared memory segments with a fixed byte capacity and map them for read/write access. Each segment carries a stable ID that other processes use to attach via offset descriptors (S4). The shared memory layer abstracts away platform differences (POSIX shm_open/mmap vs Windows CreateFileMapping/MapViewOfFile) behind a unified API.

## User Story

As a portfolio manager, I want to create a shared memory segment in one process and attach to it from another so that large financial datasets are available instantly without file I/O or network transfer.

## Scope

- In scope: Shared segment creation — allocate a named segment with a stable ID and byte capacity. Platform-specific implementation: POSIX `shm_open`/`mmap` for Linux/macOS, Windows `CreateFileMapping`/`MapViewOfFile` for Windows. Segment registry: track active segments by ID with their capacity and attach count. Segment lifecycle: create → map → detach (all attachers released) → destroy. Error returns for duplicate segment IDs, capacity overflow, failed OS-level allocation, or permission-denied mapping.
- Out of scope: Buffer wrappers (S2 — already complete). Offset descriptors (S3 — already complete). Zero-copy attach (S4 — consumes the segments created here). Provenance tracking (S6).

## Preconditions And Assumptions

- Buffer wrappers (S2) provide ownership semantics for segment data.
- Offset descriptors (S3) reference regions within segments by offset and length.
- Zero-copy attach (S4) maps segments created here into consumer processes.
- The underlying OS supports the required shared memory primitives (POSIX shm or Windows Named Shared Memory).

## Acceptance Criteria

- [ ] Given a unique segment ID and positive capacity, when a shared segment is created, then it is registered with its capacity and returns a stable segment ID.
- [ ] Given a segment creation request with a duplicate ID, when create is called, then the function returns Error (duplicate segment ID).
- [ ] Given a valid segment ID, when a process maps the segment, then the segment's memory is accessible at a stable address within the process.
- [ ] Given a segment with all attachers detached, when the segment is destroyed, then the underlying OS shared memory is released and subsequent mapping attempts return Error.
- [ ] Given a segment creation request with capacity of zero, when create is called, then the function returns Error (invalid capacity).

## Notes And Open Questions

- Segment ID generation: monotonic counter, UUID, or hash of (process ID, timestamp)? (Decision: monotonic counter per-process with global uniqueness via process ID prefix — simple and debuggable.)
- How large should the default segment capacity be? (Decision: caller-specified; no default. The caller knows the data size.)
- Should segments persist after the creating process exits? (Decision: no — segments are destroyed when the creating process exits unless explicitly persisted, which is out of scope for V1.3.)
