# V1.2.S1: Capability registry — schema and storage for mapping operations to backend implementations

**Labels:** `type/story`, `area/platform`, `type/feature`
**GitHub Issue:** #69

Define the capability registry: a central schema and storage layer that maps Yamori operation names to their backend implementations (Arrow Compute, GSL, custom). This registry is the foundation of the results engine — every computation must go through it.

## Product Outcome

The capability registry becomes the single source of truth for which backend implements each Yamori operation. No calculation bypasses the registry; every dispatch path is explicit and auditable. This eliminates hidden backends and gives operators a viewable inventory of all registered capabilities.

## User Story

As an investment analyst, I want every Yamori calculation to go through a single registry so that I never see results from a hidden or unregistered backend.

## Scope

- In scope: Capability registry type — maps operation names (strings or enums) to backend identifiers. Registry add/lookup/list/delete operations. Schema: operation name, registered backend(s), priority order for multi-backend registrations. Input validation (operation name uniqueness, backend name validity). In-memory storage. `yamori registry list` CLI scaffolding.
- Out of scope: Arrow dispatch registration (S2). GSL dispatch registration (S3). Error normalization (S4). Dispatch API (S5). Backend selection (S6). Provenance recording (S7).

## Preconditions And Assumptions

- No capability registry exists in the codebase.
- Operation names are strings; backend identifiers are strings (e.g., "arrow", "gsl", "custom").
- Multiple backends can be registered for the same operation; priority order determines default selection.
- The registry is in-memory only; persistence is deferred to V5.

## Acceptance Criteria

- [ ] Given an operation name and backend identifier, when a capability is registered, then it is stored and can be looked up by operation name.
- [ ] Given a duplicate registration for the same operation and backend, when registry add is called, then the operation returns Error (duplicate registration).
- [ ] Given an operation with no registered backend, when dispatch is attempted, then the registry returns Error (no backend registered).
- [ ] Given multiple backends registered for the same operation, when the registry is listed, then all registrations with their priority order are returned.
- [ ] Given no capabilities registered, when the registry is listed, then an empty list is returned.
- [ ] Given a registered capability, when it is removed from the registry, then subsequent lookups return Error (not registered).

### Conditional Acceptance

**Financial capability and policy**

- [ ] N/A - the registry is a routing schema, not a financial capability or policy mechanism.

**Audit and replay**

- [ ] N/A - provenance for registered operations is deferred to S7 (dispatch provenance).

**Runtime topology and tile ownership**

- [ ] N/A - no tile or topology changes. The capability registry is an in-memory data structure.

**Model, tool, adapter, or execution boundary**

- [ ] N/A - no model or adapter calls. The registry maps operation names to backend identifiers; actual dispatch is S5.

**CaseOps API or UI**

- [ ] N/A - CLI scaffolding only; no API or UI contract changes.

**Metrics, diagnostics, and operations**

- [ ] Applies - the registry must be listable to serve as operator-visible evidence of registered capabilities.

**Security and fail-closed behavior**

- [ ] Applies - unregistered operations must return Error, never a default or fallback behavior.

## Notes And Open Questions

- Should operation names be strings or a typed enum? (Decision: strings for flexibility; S2/S3 define the operation name conventions for Arrow and GSL backends.)
- Should the registry enforce a default backend per operation? (Decision: no default; if no backend is registered for an operation, dispatch returns Error.)
- Should the CLI support `yamori registry remove` or only programmatic removal? (Decision: CLI add/list only for V1.2; remove is programmatic.)
