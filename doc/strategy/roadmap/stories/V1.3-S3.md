# V1.3.S3: Offset-based descriptors — workspace-relative offsets for shared memory references

**Labels:** `type/story`, `area/platform`, `type/feature`
**GitHub Issue:** TBD

Define offset-based buffer descriptors: references to shared memory using workspace-relative byte offsets instead of process-local pointers. These descriptors prevent pointer leakage across process boundaries and enable zero-copy attachment by mapping offset ranges in shared memory.

## Product Outcome

All references to shared memory use offset-based descriptors that are safe to pass between processes. No process-local pointer escapes into the shared data layer. This ensures that every data segment exchanged between processes is described by an offset, length, and permission — not by a raw pointer that becomes invalid when the source process changes memory layout.

## User Story

As an investment analyst, I want every shared data segment to be described by an offset and length rather than a raw pointer so that I can safely pass it between processes without worrying about memory layout changes.

## Scope

- In scope: Offset-based descriptor type — fields: source segment ID, byte offset, byte length, permission flags. Descriptor validation: offset within bounds, length non-negative, permission valid. Descriptor-to-buffer mapping: resolve a descriptor to an offset within a known shared segment. Error returns for out-of-bounds offsets, negative lengths, invalid permissions. Descriptor serialization: encode/decode descriptors for inter-process transfer (fixed-size binary layout).
- Out of scope: Buffer wrappers (S2 — already complete). Zero-copy attach across processes (S4). Shared memory creation (S5). Provenance tracking (S6).

## Preconditions And Assumptions

- Buffer wrapper types (S2) provide the ownership semantics that descriptors will reference.
- Shared segments are identified by stable IDs (allocated in S5).
- Descriptors are fixed-size binary structures for safe inter-process transfer.
- Offset validation assumes the target segment's size is known at resolution time.

## Acceptance Criteria

- [ ] Given a shared segment ID, byte offset within bounds, non-negative length, and valid permission, when a descriptor is created, then it can be resolved to a valid offset-range within the segment.
- [ ] Given a descriptor with an offset beyond the segment's size, when resolved, then the function returns Error (offset out of bounds).
- [ ] Given a descriptor with a negative length, when created, then the operation returns Error (invalid descriptor).
- [ ] Given a valid descriptor, when serialized, then the binary encoding is deterministic and decodable to the original descriptor.
- [ ] Given a descriptor with invalid permission flags, when created, then the operation returns Error (invalid permission).

## Notes And Open Questions

- Should segment IDs be 32-bit or 64-bit? (Decision: 64-bit for future-proofing; segment count is not expected to exceed 2^32.)
- How do descriptors integrate with the Arrow C Data Interface layout? (Decision: descriptors wrap Arrow C Data arrays by specifying the offset range within a shared segment where the array data resides.)
- Should descriptors carry a generation counter to detect stale references? (Decision: no — stale detection is a runtime concern handled by S4/S5 attach semantics, not by the descriptor itself.)
