# V1.4.S4: Opaque handles — expose backend state as opaque pointers

**Labels:** `type/story`, `area/platform`, `type/feature`
**GitHub Issue:** #85

Define opaque pointer types that represent backend state (solvers, RNGs, shared memory buffers, computation contexts) across the C ABI. Opaque handles prevent type leakage: the consumer knows only the pointer's existence and how to pass it to other functions — not its internal layout.

## Product Outcome

Yamori's backend state (solvers, RNGs, shared memory) is exposed as opaque `void*`-style handles through the C ABI. A Python script creates a solver handle, passes it to a pricing function, and the handle is destroyed separately — the Python consumer never sees the internal struct layout and cannot corrupt it. Type safety is enforced by the ABI, not by the consumer's knowledge of internals.

## User Story

As a Python researcher, I want backend state (solvers, RNGs, shared memory) exposed as opaque handles so that I can create, use, and destroy them without understanding their internal layout or risking memory corruption.

## Scope

- In scope: Opaque handle type: `YamoHandle` (typedef `void*` with a comment explaining its purpose). Handle lifecycle functions: create (`yamo_<capability>_create`), use (`yamo_<capability>_run`), destroy (`yamo_<capability>_destroy`). Handle validation: null checks and validity checks at every function entry. Handle uniqueness: each created handle is unique and cannot be reused after destruction. Error handling: invalid handle returns `YAMO_ERR_INVALID_HANDLE`. Header file: `yamori_handle.h` with opaque type and lifecycle declarations.
- Out of scope: Handle pooling or reuse (deferred). Handle serialization across processes (V5). Handle audit trails (V5). Concurrent handle access (deferred).

## Preconditions And Assumptions

- Backend state objects exist in C++ and can be allocated/deallocated from C wrapper functions.
- Each capability that needs state has a unique handle type concept (solver, RNG, context).
- The error types (S3) are stable and provide `YAMO_ERR_INVALID_HANDLE`.

## Acceptance Criteria

- [ ] Given a capability that requires state (e.g., a solver), when `yamo_solver_create` is called, then it returns a unique, non-null `YamoHandle`.
- [ ] Given a valid `YamoHandle`, when passed to a stateful function (`yamo_solver_run`), then the function operates correctly using the handle's internal state.
- [ ] Given a `YamoHandle` that has been destroyed, when passed to any function, then the function returns `YAMO_ERR_INVALID_HANDLE` without accessing the freed memory.
- [ ] Given a null handle, when passed to any function, then the function returns `YAMO_ERR_INVALID_HANDLE` without dereferencing.
- [ ] Given two `YamoHandle` values created separately, when compared, then they are always unique (no two handles have the same pointer value).

## Notes And Open Questions

- Should handles be allocated on the heap (`malloc`) or managed through a handle table? (Decision: heap allocation for V1.4; a handle table for thread safety is deferred.)
- Should opaque handles be typed (`YamoSolverHandle`, `YamoRngHandle`) or use a single `YamoHandle` type? (Decision: single `YamoHandle` type (`void*`) for simplicity; the ABI contract specifies which capabilities accept which handles.)
- Can handles be shared between threads? (Decision: not in V1.4; thread safety is deferred. The consumer must ensure single-threaded access to each handle.)
