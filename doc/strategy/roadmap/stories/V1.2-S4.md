# V1.2.S4: Error normalization — all backend failures return Yamori !Error types

**Labels:** `type/story`, `area/platform`, `type/feature`
**GitHub Issue:** #72

Define and implement Yamori's unified `!Error` type and the normalization layer that converts all backend-specific errors (Arrow errors, GSL errors, custom kernel errors) into typed Yamori errors. This guarantees that no Arrow, GSL, or third-party type leaks into Yamori's public API and that users always see clear, actionable error messages.

## Product Outcome

Every backend failure — whether from Arrow, GSL, or a custom kernel — is transformed into a Yamori `!Error` with a clear category and actionable message. Users see "source metric missing" or "backend unavailable", never "Arrow status code 42" or "gsl_eigen failure". The public API of Yamori never exposes a backend-specific type. This is a trust signal: the system controls its own error vocabulary.

## User Story

As a portfolio manager, I want to see clear, actionable error messages when a backend fails, so that I can diagnose the issue without understanding which computational library is running underneath.

## Scope

- In scope: Yamori `!Error` enum/struct with categories: `NotRegistered`, `BackendUnavailable`, `InvalidInput`, `BackendFailure`, `InternalError`. Error message formatting: human-readable, actionable messages per category. Normalization layer: `normalize_arrow_error(arrow_error) -> !Error`, `normalize_gsl_error(gsl_error) -> !Error`, `normalize_generic_error(msg) -> !Error`. S2 adapter integration: Arrow errors normalized before returning to caller. S3 adapter integration: GSL errors normalized before returning to caller. Verification: dispatch an operation that triggers each error category and verify the returned type is `!Error` with the correct category.
- Out of scope: User-facing error UI (V5). Error logging infrastructure (S7 provenance). Backend selection (S6). Provenance recording (S7).

## Preconditions And Assumptions

- S1 (capability registry) is implemented and can return `NotRegistered` errors.
- S2 (Arrow adapter) is implemented and can raise Arrow errors.
- S3 (GSL adapter) is implemented and can raise GSL errors.
- The `!Error` type is defined in Yamori's public API; all backends must return through this type.
- Error messages are formatted for human readability; machine-parsable fields (category enum) are also available.

## Acceptance Criteria

- [ ] Given an unregistered operation is dispatched, when the registry lookup fails, then the returned error is `!Error(NotRegistered)` with a message like "no backend registered for operation 'X'".
- [ ] Given an Arrow operation fails (e.g., division by zero in Arrow), when the Arrow adapter catches the error, then it returns `!Error(BackendFailure)` with a normalized message (not a raw Arrow error type).
- [ ] Given a GSL operation fails (e.g., invalid input to GSL regression), when the GSL adapter catches the error, then it returns `!Error(BackendFailure)` with a normalized message (not a raw GSL error type).
- [ ] Given an operation with invalid inputs (e.g., empty array), when the dispatch layer validates inputs, then it returns `!Error(InvalidInput)` with a message specifying which input was invalid.
- [ ] Given an internal error in the dispatch layer (e.g., assertion failure), when the error is caught, then it returns `!Error(InternalError)` — never a raw panic or undefined behavior.
- [ ] Zero Arrow or GSL types appear in Yamori's public API. All error types in public headers are Yamori `!Error` variants.

## Notes And Open Questions

- Should `!Error` include machine-parsable fields (operation name, backend name) for automation? (Decision: yes, include optional context fields in the `!Error` struct for machine parsing while keeping the human-readable message primary.)
- Should the normalization layer be a standalone module or inline in each adapter? (Decision: standalone normalization module that adapters call; keeps the normalization logic DRY and testable independently.)
- Should internal errors be logged before being returned as `!Error(InternalError)`? (Decision: yes, log at warn level with the full error details internally; only the category and a generic message are returned to callers.)
