# V1.5.S4: Reduction order — fixed floating-point reduction order

**Labels:** `type/story`, `area/platform`, `type/feature`
**GitHub Issue:** #92

Eliminate floating-point non-determinism from reductions by enforcing a fixed, documented reduction order. Parallel sums, products, and aggregations always produce the same result regardless of thread scheduling.

## Product Outcome

Every floating-point reduction in Yamori follows a fixed, documented order. Operators can trust that summing a thousand cash flows on Linux x86 produces the same result as summing them on macOS ARM — because the reduction order is the same, not because the platform happens to agree.

## User Story

As a data researcher, I want every floating-point reduction to use a fixed order, so that I can add a new financial formula and inherit reproducibility automatically — no additional configuration required.

## Scope

- In scope: identify all floating-point reductions (sums, products, averages, aggregations), replace parallel reductions with a deterministic sequential order, or implement a deterministic tree reduction, enforce fixed order via comptime or runtime config.
- Out of scope: algorithm pinning (S1), RNG pinning (S2), threading policy (S3), fast-math (S5), harness (S6), provenance (S7).

## Preconditions And Assumptions

- V1.5.S3 (threading policy) fixes thread count; S4 uses that fixed count to ensure reduction determinism.
- Yamori currently uses reductions in DCF calculations, portfolio aggregations, and other numerical kernels.
- The standard library or runtime does not provide a deterministic reduction; one must be implemented.

## Acceptance Criteria

- [ ] Given a list of floating-point values, when a reduction (sum, product, average) is applied, then the result is identical on all four target platforms.
- [ ] Given a parallel reduction that would produce different results under different scheduling orders, when the deterministic reduction order is enforced, then the result is the same regardless of thread scheduling.
- [ ] Given a floating-point reduction with more than one value, when the values are in a different input order, then the result may differ (documented limitation — order matters, and that order is fixed).
- [ ] No use of non-deterministic parallel reduction (e.g., `std.parallelism.reduce` with unordered merge) in any Yamori numerical kernel.

## Notes And Open Questions

- Should reductions use a fixed sequential order (simplest, slowest on large datasets) or a deterministic tree reduction (faster but more complex)? The answer depends on the performance profile of the target workloads.
- Kahan summation or compensated summation could reduce floating-point drift even within a fixed order — should it be adopted as part of S4 or deferred?
