# V1.3.S4: Zero-copy attach — multiple processes map the same underlying data via offset descriptors

**Labels:** `type/story`, `area/platform`, `type/feature`
**GitHub Issue:** #79

Implement zero-copy attach: the ability for multiple processes to map the same underlying shared memory segment via offset descriptors, without copying any bytes. When one process creates a shared segment and publishes its descriptor, other processes attach to it and gain direct, zero-copy access to the data.

## Product Outcome

Multiple computational processes access the same underlying data without any byte copying. When a valuation engine publishes results and a sensitivity analyzer attaches to them, the data is already there — directly accessible through mapped memory. This delivers the performance of shared memory with the safety of structured, auditable data exchange.

## User Story

As a data researcher, I want to launch a sensitivity analysis process that reads the same dataset as my valuation process without any export, serialization, or file I/O so that I get instantaneous access to the data I need.

## Scope

- In scope: Attach API — `attachSharedBuffer()` function that takes a segment ID and offset descriptor, maps the shared segment into the attaching process's address space, and returns a local reference. Attach validation: segment ID must exist, descriptor must resolve within bounds, attaching process must have permission. Detach API: release a local attachment without affecting the shared segment or other attachers. Reference counting for attach count (segment is only freed when all attachers detach). Error returns for invalid segment ID, failed mapping, or permission violations.
- Out of scope: Buffer wrappers (S2 — already complete). Offset descriptors (S3 — already complete). Shared memory creation (S5 — provides the segment that attach maps). Provenance tracking (S6).

## Preconditions And Assumptions

- Shared segments are created by a producer process (S5).
- Offset descriptors (S3) describe which regions of a segment to attach.
- Buffer wrappers (S2) provide ownership semantics for attached data.
- The underlying OS supports shared memory creation and mapping (POSIX shm_open/mmap or Windows Named Shared Memory).

## Acceptance Criteria

- [ ] Given a shared segment created by a producer process, when a consumer process attaches via a valid offset descriptor, then the consumer gains direct access to the segment's data without any byte copying.
- [ ] Given a shared segment with multiple attachers, when one attacher detaches, then the segment remains available to the remaining attachers.
- [ ] Given an attach request with an invalid segment ID, when attach is called, then the function returns Error (segment not found).
- [ ] Given an attach request with a descriptor whose offset is out of bounds, when attach is called, then the function returns Error (invalid descriptor).
- [ ] Given a shared segment with zero active attachers, when the producer releases it, then the segment is freed and subsequent attach attempts return Error.

## Notes And Open Questions

- Which shared memory API should the attach layer use: POSIX `shm_open`/`mmap` or Windows Named Shared Memory? (Decision: abstract behind a platform shim — S5 implements the platform-specific creation; S4 calls the unified API.)
- Should the attach API return a buffer wrapper (S2) directly, or a separate attachment handle? (Decision: return a borrowed buffer wrapper referencing the mapped memory — this keeps the ownership model consistent.)
- How does the attach API handle a segment that is being written by the producer while a consumer is reading? (Decision: no concurrent write protection — this is a producer responsibility. Document that writers must synchronize access; concurrency safety is V2+.)
