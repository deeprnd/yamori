# V1.4.S7: ABI documentation — every function documents its contract, types, and error conditions

**Labels:** `type/story`, `area/platform`, `type/documentation`
**GitHub Issue:** #88

Document every ABI-exposed function with its complete contract: function name, parameter types, return type, error conditions, and usage examples. This is the consumer contract — the single source of truth that every language binding (Python, Rust, Go) references to implement correct consumption.

## Product Outcome

Every C ABI function has a complete, machine-readable and human-readable contract that describes its inputs, outputs, error conditions, and usage. A Rust developer reading the ABI docs can implement a correct binding without reverse-engineering the C header. The documentation is the authoritative reference for all language consumers.

## User Story

As a Rust developer, I want every ABI function documented with its full contract so that I can implement a correct binding without reading the C source or guessing at error conditions.

## Scope

- In scope: Per-function documentation: function name, purpose, parameters (with type descriptions), return value (with type description), error conditions (which `YamoStatus` codes and when), usage examples (C code snippet). Struct documentation: field descriptions, layout notes, alignment requirements. Enum documentation: all `YamoStatus` values with descriptions. Error function documentation: when to call, what it returns. Usage examples: at least one C example per capability showing create/use/destroy lifecycle. Machine-readable contract: a structured JSON or YAML file describing every function's signature and types (for binding generators).
- Out of scope: Automated binding generation (V5). Multi-language examples (V5). Interactive documentation site (V5).

## Preconditions And Assumptions

- The C ABI surface (S1–S4) is stable enough to document.
- The ABI tests (S5) confirm the surface is frozen for release.
- Documentation follows the project's doc conventions (`doc/execution/quality.md`).

## Acceptance Criteria

- [ ] Given every ABI-exposed function, when its documentation is read, then it includes a purpose description, parameter list with types, return type, and all possible error conditions.
- [ ] Given every ABI-exposed struct, when its documentation is read, then it includes a field-by-field description and alignment/layout notes.
- [ ] Given every `YamoStatus` enum value, when its documentation is read, then it includes a description of when that status is returned.
- [ ] Given each capability with state (solvers, RNGs), when its documentation is read, then it includes a complete create/use/destroy usage example in C.
- [ ] Given the machine-readable contract file, when parsed, then it contains the same information as the human-readable documentation (consistency check).

## Notes And Open Questions

- Should the ABI documentation live alongside the header file (`yamori_c.h`) or in a separate documentation directory? (Decision: separate directory `doc/abi/` for discoverability; the header file is minimal and code-only.)
- Should the machine-readable contract be a JSON file or a YAML file? (Decision: JSON for broader tooling support; YAML is more human-friendly but JSON is more universally parsable.)
- Who maintains the ABI documentation when functions change? (Decision: the story that changes a function is responsible for updating its documentation. The ABI test (S5) gate ensures documentation changes are not forgotten.)
