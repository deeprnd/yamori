# V1.2.S6: Backend selection — runtime or compile-time selection of backend per operation

**Labels:** `type/story`, `area/platform`, `type/feature`
**GitHub Issue:** #74

Implement backend selection: the mechanism by which Yamori chooses which registered backend to use when dispatching an operation. Supports both compile-time defaults (build configuration) and runtime overrides (configuration or environment variable), enabling operators to swap backends without code changes.

## Product Outcome

Operators can select which backend powers each operation — at compile time via build flags or at runtime via configuration. This means Yamori can be built with Arrow as the default and switched to GSL for comparison, or vice versa, without any code changes. Backend selection is transparent to domain code: the `dispatch()` API remains unchanged.

## User Story

As a data researcher, I want to swap the computational engine behind a calculation and verify the results haven't changed, so that I can compare backends and validate reproducibility without modifying domain code.

## Scope

- In scope: Compile-time backend selection: build flags (e.g., `--default-backend=arrow` or `--default-backend=gsl`) that set the default backend for all unselected operations. Runtime backend selection: configuration option or environment variable (e.g., `YAMORI_DEFAULT_BACKEND=arrow`) that overrides the compile-time default. Per-operation backend override: configuration entries like `mean=gsl`, `divide=arrow` to select specific backends per operation. Integration with dispatch (S5): `dispatch()` reads the selected backend and routes accordingly. Verification: build with different compile-time defaults, dispatch the same operation, verify the correct backend is used.
- Out of scope: Dynamic backend swapping during execution (deferred). Backend health monitoring (V5). Provenance recording of selected backend (S7). Error normalization (S4).

## Preconditions And Assumptions

- S1 (capability registry) supports multiple backends per operation with priority order.
- S5 (dispatch API) is implemented and routes to backends via the registry.
- Compile-time defaults are set via build configuration (e.g., Zig build flags).
- Runtime defaults are set via environment variable or config file.
- Per-operation overrides take precedence over the default selection.

## Acceptance Criteria

- [ ] Given the build is configured with `--default-backend=gsl`, when an operation with both Arrow and GSL registered is dispatched, then the GSL backend is selected as the default.
- [ ] Given the environment variable `YAMORI_DEFAULT_BACKEND=arrow` is set, when the runtime loads configuration, then the default backend is overridden to Arrow (regardless of compile-time default).
- [ ] Given a per-operation override `mean=gsl` in the configuration, when `dispatch("mean", ...)` is called, then the GSL backend is selected even if the default is Arrow.
- [ ] Given a per-operation override takes precedence, when both the default and a per-operation override are set, then the per-operation override is used.
- [ ] Given no default is set (neither compile-time nor runtime), when dispatch is called, then the registry's highest-priority registered backend is used as a fallback.
- [ ] Given an explicitly selected backend is not registered for the operation, when dispatch is called, then it returns `!Error(BackendUnavailable)` with a clear message.

## Notes And Open Questions

- Should backend selection support per-operation selection via command-line flags or only via config? (Decision: config file or environment variable only for V1.2; CLI per-op flags are M2+.)
- Should backend selection be hot-swappable (change at runtime without restart)? (Decision: no for V1.2; configuration is read at dispatch initialization. Hot-swapping is M2+.)
- Should the configuration schema be YAML, JSON, or a simple key-value format? (Decision: key-value format for V1.2 simplicity; richer formats are M2+.)
