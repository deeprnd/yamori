# V1.2.S3: GSL adapter dispatch — register GSL statistical functions behind the capability registry

**Labels:** `type/story`, `area/platform`, `type/feature`
**GitHub Issue:** #71

Register GSL (GNU Scientific Library) statistical functions behind the capability registry established in S1. This maps GSL function names (e.g., linear regression, correlation, mean, variance) to the Yamori operation namespace, enabling GSL-backed calculations alongside Arrow.

## Product Outcome

GSL statistical functions become available as backends for the capability registry. Domain code can request GSL-backed statistical operations through the same normalized dispatch API used for Arrow — no knowledge of which backend is powering each calculation. This gives Yamori a second, independent computational backend that can serve operations Arrow does not natively support.

## User Story

As an investment analyst, I want statistical functions like linear regression and correlation available through the same dispatch layer as basic arithmetic, so that complex analysis uses the right tool regardless of which backend provides it.

## Scope

- In scope: GSL adapter module that wraps GSL library calls. Registration of GSL-backed operations into the capability registry (S1). Mapping of GSL function names to Yamori operation names (e.g., "linear_regression", "correlation", "mean", "variance"). Input normalization: convert Yamori input types to GSL-compatible types (double arrays). Error capture: convert GSL errors to Yamori `!Error` types (deferred normalization, S4). Dispatch test: register a GSL operation, dispatch through S1 registry, verify result.
- Out of scope: Arrow dispatch (S2). Error normalization (S4). Backend selection logic (S6). Provenance recording (S7). GSL data source conversion (V1.3).

## Preconditions And Assumptions

- The capability registry (S1) is implemented and provides add/lookup/list/remove operations.
- GSL is available as a dependency; the adapter will link against the GSL C library.
- GSL function names serve as the canonical operation identifiers (e.g., "linear_regression" → `gsl_stats_linear_regression`).
- GSL errors are captured by the adapter and will be normalized in S4.
- GSL operates on double-precision arrays; the adapter handles type conversion from Yamori inputs.

## Acceptance Criteria

- [ ] Given the GSL adapter, when `register_gsl_backends(registry)` is called, then all supported GSL operations are registered in the capability registry with backend identifier "gsl".
- [ ] Given a GSL-backed operation is registered, when dispatch is invoked through the registry with that operation name, then the GSL function is called with normalized inputs and a result is returned.
- [ ] Given a GSL operation is dispatched with valid inputs, when the result is returned, then it matches the expected GSL output (verified by golden test).
- [ ] Given a GSL operation is dispatched with invalid inputs (e.g., NaN, empty array), when the GSL call fails, then the error is captured and returned as a Yamori `!Error` type (not a raw GSL error).
- [ ] Given both Arrow and GSL backends are registered for the same operation (e.g., "mean"), when each is dispatched independently with the same input, then both produce numerically equivalent results within floating-point tolerance.

## Notes And Open Questions

- Which GSL functions are in scope for V1.2? (Decision: linear_regression, correlation, mean, variance, covariance — the statistical operations most needed for financial analysis.)
- Should the GSL adapter handle data source conversion (e.g., CSV → GSL arrays)? (Decision: no. Data source conversion is V1.3. The adapter receives pre-converted double arrays from the caller.)
- Should the GSL adapter support multi-threading via GSL's OpenMP integration? (Decision: no for V1.2; GSL runs single-threaded. Multi-threading is M2+.)
