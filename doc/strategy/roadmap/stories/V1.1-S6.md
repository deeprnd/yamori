# V1.1.S6: Graph re-evaluation — change one leaf and recompute affected subtree

**Labels:** `type/story`, `area/platform`, `type/feature`
**GitHub Issue:** #67

Implement graph re-evaluation: when one leaf metric changes, recompute only the affected subtree of the dependency graph instead of recomputing the entire graph.

## Product Outcome

Users can change a single source metric and see only the derived metrics that depend on it update, with the system automatically identifying and recomputing the affected subtree. This enables fast sensitivity exploration: users can tweak one input and see the ripple effects without waiting for a full recomputation.

## User Story

As a portfolio manager, I want to change one input metric and see only the affected derived metrics update, so that I can run sensitivity scenarios quickly without recomputing the entire model.

## Scope

- In scope: Identify the leaf metric that changed. Trace all formulas that depend on it (directly or transitively). Recompute only those formulas in topological order. Preserve unchanged results. Integrate with `runValuation()` (S5).
- Out of scope: User-facing sensitivity UI (M4, V4.14–V4.15). Monte Carlo engine (M4, V4.17–V4.20). Provenance (S7).

## Preconditions And Assumptions

- The full dependency graph (S1, S2) is built and cached.
- Leaf metrics are identified by having no incoming edges in the dependency graph (they are not referenced as sources by any other formula).
- The result frame from `runValuation()` (S5) is available as the base state.

## Acceptance Criteria

- [ ] Given a graph A→B→C (C depends on B, B depends on A) and a change to leaf metric A, when re-evaluation runs, then B and C are recomputed, A's result is unchanged (it is a source), and the output contains all three results.
- [ ] Given a graph with two independent chains (A→B and X→Y) and a change to A, when re-evaluation runs, then only B is recomputed; X and Y are unchanged.
- [ ] Given a diamond dependency (A→B, A→C, B→D, C→D) and a change to A, when re-evaluation runs, then B, C, and D are recomputed in correct order.
- [ ] Given a change to a non-leaf metric B (B is referenced by D), when re-evaluation runs, then only D is recomputed (not A).
- [ ] Given a change to a metric with no dependents (a leaf that no formula depends on), when re-evaluation runs, then no formulas are recomputed (only the source is updated).

## Notes And Open Questions

- Should the reverse adjacency list be built lazily (on first re-evaluation) or eagerly (at graph build time)? (Decision: eagerly — O(V+E) cost is negligible for formula graphs.)
- Should re-evaluation support partial updates (e.g., update one period of a time series) or only full array swaps? (Decision: full array swaps for V1.1; partial updates are V3.)
