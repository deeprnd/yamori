# V1.5.S3: Threading policy — deterministic thread count and scheduling

**Labels:** `type/story`, `area/platform`, `type/feature`
**GitHub Issue:** #91

Enforce a deterministic threading policy: thread count and scheduling order are fixed and reproducible, eliminating non-determinism from parallel execution.

## Product Outcome

Yamori's parallel execution uses a fixed, explicit thread count with deterministic scheduling. Operators know exactly how many threads are active and in what order work is dispatched — reproducibility is not left to the scheduler.

## User Story

As a portfolio manager, I want Yamori's parallel computations to use a fixed, documented thread count, so that the execution timeline is predictable and reproducible across runs.

## Scope

- In scope: define a deterministic threading policy, enforce explicit thread count at the API level, replace any auto-scaling or OS-dependent thread pool sizing with a fixed count, ensure work partitioning is deterministic.
- Out of scope: algorithm pinning (S1), RNG pinning (S2), reduction order (S4), fast-math (S5), harness (S6), provenance (S7).

## Preconditions And Assum assumptions

- Yamori uses a tile-based runtime (Firedancer substrate) where tiles handle parallel work. The threading policy must be compatible with the tile topology.
- V1.5.S1–S2 establish the base determinism framework.
- A work partitioning mechanism exists (or must be added) that respects thread count boundaries.

## Acceptance Criteria

- [ ] Given a deterministic run request, when the computation starts, then the thread count is explicitly set and does not vary across runs or platforms.
- [ ] Given a work partition that would be scheduled differently on different thread counts, when a fixed thread count is enforced, then the partitioning and scheduling order are identical across runs.
- [ ] Given an invalid or zero thread count, when a run is requested, then the call returns `Error`.
- [ ] No implicit thread pool sizing (e.g., `std.Thread.pool` auto-sizing) is used for any Yamori computation.

## Notes And Open Questions

- Should thread count be a per-run parameter or a global config? Per-run offers flexibility but adds API surface; global config is simpler but less adaptable.
- How does the threading policy interact with the Firedancer tile topology? Tiles may have their own internal parallelism; the policy must cover both tile-level and intra-tile parallelism.
