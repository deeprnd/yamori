# V1.4.S3: Error types — stable C types for Yamori status codes and error messages

**Labels:** `type/story`, `area/platform`, `type/feature`
**GitHub Issue:** #84

Define stable C types for Yamori's error and status handling: a `YamoStatus` enum for all possible outcomes, error codes for each failure mode, and an error message function that returns a human-readable string. This ensures every language consumer receives typed, consistent errors — no C++ exceptions, no undefined behavior.

## Product Outcome

Every Yamori C function returns a typed status code (`YAMO_OK`, `YAMO_ERR_INVALID_INPUT`, `YAMO_ERR_NOT_FOUND`, etc.) and provides a mechanism to retrieve a human-readable error message. Python, Rust, and Go consumers all see the same error codes and can handle them programmatically. No C++ exceptions leak across the boundary.

## User Story

As a Rust developer, I want Yamori's errors exposed as stable C types so that I can handle them with match statements and get meaningful error messages without C++ exception handling.

## Scope

- In scope: `YamoStatus` enum with all possible values (OK, invalid input, not found, not implemented, internal error, buffer overflow, timeout). `YamoError` struct with status code and optional message string. Error message function: `yamo_error_message(YamoStatus)` returns a static, null-terminated string for known statuses. Error propagation: wrapper functions map internal errors to `YamoStatus` values before returning. Header file: `yamori_error.h` with enum, struct, and function declarations.
- Out of scope: Error recovery mechanisms (deferred). Error logging infrastructure (deferred). C++ exception translation layer (deferred). Error serialization for audit (V5).

## Preconditions And Assumptions

- The error enum values are stable and cover all failure modes the runtime can produce.
- Error messages are static strings (no dynamic allocation at error time).
- The C wrapper layer (S1) calls error message functions before returning status codes.

## Acceptance Criteria

- [ ] Given a `YamoStatus` value of `YAMO_OK`, when `yamo_error_message` is called, then it returns a static string "OK".
- [ ] Given a `YamoStatus` value of `YAMO_ERR_INVALID_INPUT`, when `yamo_error_message` is called, then it returns a non-empty static string describing the error.
- [ ] Given an unknown `YamoStatus` value, when `yamo_error_message` is called, then it returns a generic "Unknown error" string (fail-safe).
- [ ] Given a wrapper function that encounters an internal error, when it returns to the C consumer, then the status code is one of the defined `YamoStatus` values (never an undefined or out-of-range value).
- [ ] Given the `YamoStatus` enum, when compiled from a C source file, then all enum values have stable integer representations across compilers.

## Notes And Open Questions

- Should error messages include context (e.g., which function failed) or be static? (Decision: static messages for V1.4; per-function context is V5.)
- Should `YamoStatus` values start at 0 or 1? (Decision: `YAMO_OK` = 0, errors start at 1 — follows C convention.)
- Should the enum use `int32_t` or the default `int` size? (Decision: default `int` for simplicity; ABI stability comes from the enum's fixed values, not its size, since C enums are always passed as integers.)
