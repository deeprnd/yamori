# V1.2.S7: Dispatch provenance — every operation records backend, inputs, and output

**Labels:** `type/story`, `area/platform`, `type/feature`
**GitHub Issue:** TBD

Record provenance metadata for every dispatched operation: which backend ran it, with what inputs, and what output it produced. This creates an auditable trail of all computations through the results engine, enabling operators to verify that every calculation went through the correct backend and produces reproducible results.

## Product Outcome

Every computation through the results engine is accompanied by provenance metadata: backend identifier, input summary, output summary, and a unique provenance ID. Operators can query provenance for any operation to verify which backend executed it and with what parameters. This is the audit trail of the results engine — every dispatch is traceable from input to output to backend.

## User Story

As a compliance reviewer, I want to audit any calculation's provenance — which backend ran it, with what inputs, and what result it produced — so that I can verify the integrity of the entire computation chain.

## Scope

- In scope: Provenance metadata struct: operation name, backend identifier, input summary (hash or serialized representation), output summary (hash or serialized representation), provenance ID (unique per dispatch). Provenance recording: `dispatch()` (S5) calls a provenance recorder after each successful or failed dispatch. Provenance storage: in-memory buffer of recent provenance records (size-limited, LRU). Provenance query: `query_provenance(op_name) -> [ProvenanceRecord]` to retrieve recent records for an operation. Provenance ID generation: deterministic or UUID-based (decision pending). Integration with dispatch: every dispatch — successful or failed — records provenance.
- Out of scope: Persistent provenance storage (V5). Provenance export/import (V5). Provenance-based replay (V5). Backend selection (S6). Error normalization (S4).

## Preconditions And Assumptions

- S5 (dispatch API) is implemented and calls the dispatch function.
- S4 (error normalization) is implemented and provides consistent error types.
- Provenance is in-memory only; persistence is deferred to V5.
- Input/output summaries are hashes or abbreviated representations (not full data serialization) to avoid memory bloat.
- Provenance records are created for all dispatches — successful or failed.

## Acceptance Criteria

- [ ] Given any operation is dispatched, when the dispatch completes (success or failure), then a provenance record is created with: operation name, backend identifier, input summary, output summary (or error category), and a unique provenance ID.
- [ ] Given multiple operations are dispatched, when provenance records are queried by operation name, then all records for that operation are returned in dispatch order.
- [ ] Given the provenance buffer is full (size limit reached), when a new record is added, then the oldest record is evicted (LRU policy).
- [ ] Given a dispatch fails with an error, when the provenance record is created, then it includes the error category (from S4) instead of an output summary.
- [ ] Given two identical operations are dispatched with the same inputs, when both provenance records are compared, then they have different provenance IDs but identical input summaries.
- [ ] Given zero operations are dispatched, when provenance is queried, then an empty list is returned.

## Notes And Open Questions

- Should provenance IDs be deterministic (hash of inputs+operation+backend) or random (UUID)? (Decision: deterministic for reproducibility — same inputs produce the same provenance ID.)
- Should provenance include timestamps? (Decision: yes, include timestamps for operational visibility, but they are not part of the provenance ID hash.)
- Should the provenance buffer be persisted to disk periodically? (Decision: no for V1.2; persistence is V5. The buffer is in-memory only.)
- What is the provenance buffer size limit? (Decision: configurable, default 1000 records. Varies by deployment.)
