# V1.1.S6: Graph Re-evaluation — Selective Recomputation of Affected Subtrees

## Story Summary

Implement graph re-evaluation: when one leaf metric changes, recompute only the affected subtree of the dependency graph instead of recomputing the entire graph.

**What this delivers:** Users can change a single source metric and see only the derived metrics that depend on it update. The system automatically identifies and recomputes the affected subtree. This enables fast sensitivity exploration.

**What this does NOT deliver:** User-facing sensitivity UI (M4). Monte Carlo engine (M4). Provenance (S7).

## Data Structures

### `ReverseAdjacencyList` — Pre-computed

```zig
pub const ReverseAdjacencyList = struct {
    // name → list of formulas that depend on this name
    dependents: std.StringHashMap(std.ArrayList([]const u8)),
    allocator: std.mem.Allocator,
};
```

### `ReEvaluationInput`

```zig
pub const ReEvaluationInput = struct {
    leaf_name: []const u8,            // which leaf metric changed
    new_value: *Array,                // new float64 array for the leaf
    registry: *const FormulaRegistry, // S1
    reverse_adj: *const ReverseAdjacencyList, // pre-computed dependents map
    current_results: *const ResultFrame, // S5 output, used as base state
};
```

### `ReEvaluationResult`

```zig
pub const ReEvaluationResult = struct {
    // Only the changed results (delta)
    changed_results: std.StringHashMap(*Array),
    unchanged_keys: []const []const u8, // names that didn't change
    allocator: std.mem.Allocator,
};
```

### `ReEvaluationError`

```zig
pub const ReEvaluationError = error{
    LeafNotFound,         // changed metric not in registry or source data
    CycleDetected,        // should not happen if S3 is enforced
    RegistryError,        // from S1
    ResolveError,         // from S2
    ArrowError,           // from S4
    AllocationFailed,
};
```

## Unit Tests

|---------|----------|-------|-----------------|
| `test_linear_chain_change` | A→B→C, change A | B and C depend on upstream | B and C recomputed, A unchanged |
| `test_independent_changes` | Two chains: A→B and X→Y, change A | Independent chains | B recomputed; X and Y unchanged |

| `test_complex_subtree` | 6 formulas: A→B, A→C, B→D, C→D, D→E, change A | Complex graph | B, C, D, E recomputed; correct topological order |

**Total: 7 unit tests**

## Implementation Approach

1. **Start with stubs.** Implement `recomputeAffected` returning hardcoded delta results. Tests pass with stubs.
2. **Implement `buildReverseAdjacency`.** Eagerly build the dependents map from the registry. This is O(V+E) and done once at graph build time.
3. **Implement affected subtree identification.** Given `leaf_name`, do a BFS/DFS through the reverse adjacency list to find all downstream formulas. Use a `visited` set to avoid recomputing nodes multiple times.
4. **Recompute affected formulas in topological order.** Filter the full topological order (S2) to only include affected formulas. Execute via Arrow adapter (S4).
5. **Merge with unchanged results.** The result contains recomputed values for affected formulas + original values for unchanged formulas.

**Key data structure:** The reverse adjacency list is the critical optimization. Without it, you'd need to scan the entire registry for each changed leaf. With it, you follow pre-built edges.

## Notes

- The reverse adjacency list is built **eagerly** at graph build time, not lazily on first re-evaluation. The O(V+E) cost is negligible for formula graphs.
- For V1.1, re-evaluation supports full array swaps (not partial period updates). Partial updates are V3.
- This is the foundation for sensitivity analysis (M4) and Monte Carlo simulation (M4).
