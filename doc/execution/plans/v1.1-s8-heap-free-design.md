# S8: Heap-Free Design — Caller-Owned Buffers for Industrial Use

## Problem

Yamori is a **library**, not an application. It has **519 allocator references** across 10 source files (~6,500 lines). Every public API surface allocates from the heap:

- `FormulaRegistry.formulas` uses `StringHashMap` — per-formula allocations
- `registryAdd` does 12+ allocations per call (name, operation, sources)
- `detectCycleBeforeAdd` allocates adjacency list + colors + path list
- `resolveDependencies` allocates dep_list, in_degree, queue, result
- `runValuation` creates ResultFrame + ArrowArrays + f64 buffers per formula
- `dispatch` allocates output buffer per call (`gpa.alloc(f64, ...)`)
- `GSLFunctionRegistry.register` does 3 `dupe()` + 1 `create()` per capability
- `ProvenanceBuffer.init` takes an allocator; `capture()` does `gpa.alloc(usize, ...)` + `gpa.dupe(u8, ...)`
- `BackendSelector` uses `StringHashMap` (runtime overrides)

In an industrial environment where heap allocation is forbidden, **every public API is broken**.

The core issue: Yamori's library owns no memory. Its callers own everything. But the library currently calls `gpa.alloc` / `gpa.dupe` internally, reaching into the caller's allocator without the caller's knowledge or control.

---

## Design: Everything Caller-Allocated, Zero Library-Owned Heap

### Core Principle

Yamori never calls `gpa.alloc`, `gpa.dupe`, or `gpa.create`. Every data structure the library produces lives in buffers the caller provides. Two categories:

1. **Init-time buffers** — passed once at library init (registries, string tables, capability tables). The caller allocates these once, hands them to Yamori, and Yamori uses them for the lifetime of the library instance.
2. **Per-call buffers** — passed with every API call (result buffers, scratch buffers, provenance records). The caller allocates these per-call (or reuses a pool).

---

### 0. FixedBufferAllocator — std.heap.FixedBufferAllocator

Zig's `std.heap.FixedBufferAllocator` is a heap-free `std.mem.Allocator` backed by a caller-provided `[]u8`. It is the **only** allocator Yamori may use internally — and even then, only when its caller passes a FixedBufferAllocator that points at caller-owned memory.

```zig
const FixedBufferAllocator = std.heap.FixedBufferAllocator;

// Caller owns the buffer; Yamori gets an Allocator wrapper:
var scratch: [8192]u8 = undefined;
var fba = FixedBufferAllocator.init(&scratch);
const buf_alloc: std.mem.Allocator = fba.allocator();

// Yamori internals call buf_alloc.alloc(f64, 256) — data lives in scratch.
// fba.allocator().free(data) is a no-op.
// If scratch is exhausted, alloc returns null → error.OutOfMemory propagates.
```

Key properties:
- `fba.allocator()` → `std.mem.Allocator` vtable. Pass to any Yamori function expecting `allocator`.
- `alloc` succeeds within buffer capacity; returns `null` when exhausted (caller gets `error.OutOfMemory`).
- `free` is a no-op (caller controls lifetime via `fba.reset()`).
- `resize` succeeds for shrink; returns `false` for grow beyond current slot.
- `fba.reset()` → clears the offset, reuses the same buffer from the start.
- `fba.threadSafeAllocator()` → atomic `cmpxchg` variant for multi-threaded use (Yamori's single-threaded dispatch path doesn't need it).

**This is the mechanism, not the ownership.** The caller owns the underlying `[]u8`. Yamori just gets an `Allocator` to work with.

### 7. Arrow Adapter — FixedBufferAllocator, Not Heap

Arrow's `executeOperation` still takes an `allocator: std.mem.Allocator` parameter, but Yamori callers **always** pass a `FixedBufferAllocator` wrapping caller-owned memory.

```zig
// Arrow adapter signature (unchanged from library perspective):
executeOperation(op_name: []const u8,
                 operands: []const *ArrowArray,
                 allocator: std.mem.Allocator) → AdapterError!ArrowComputeResult

// Caller:
var result_buf: [MaxResultElements]f64 = undefined;
var result_fba = FixedBufferAllocator.init(
    @as([*]u8, @ptrCast(&result_buf))[0..result_buf.len * @sizeOf(f64)],
);
const result = try arrowAdapter.executeOperation(op_name, operands, result_fba.allocator());
// result.data, result.buffers_holder point into result_buf.
// computeResultFree(result) → alloc.free() is a no-op.
```

**Heap allocation audit for Arrow:**
- `executeOperation` does `allocator.alloc(f64, len)` for output → now backed by caller's `result_buf` via `FixedBufferAllocator`.
- `ArrowComputeResult` carries `data[]` and `buffers_holder` → both point into caller buffer.
- `computeResultFree()` → `free()` is no-op on `FixedBufferAllocator`; ArrowArray struct is stack-allocated by caller.
- `ArrowFunctionRegistry` → replaced by comptime `ArrowComputeMap.all` (no heap, no registry).

### 8. GSL Adapter — Already Heap-Free at Compute Level

GSL functions are pure C functions that take `[*]const f64` pointers and return `f64`. **Zero heap allocations in the computation path.**

```zig
// gsl_bindings.zig — all of these: zero allocations
pub fn mean(data: []const f64) f64
pub fn variance(data: []const f64) f64
pub fn sd(data: []const f64) f64
pub fn covariance(data1, data2: []const f64) f64
pub fn correlation(data1, data2: []const f64) f64
pub fn quantile(sorted_data: []const f64, f: f64) f64
pub fn median(sorted_data: []const f64) f64
```

The **only** heap allocations in GSL are registration-time:
- `GSLFunctionRegistry.register` → replaced by comptime `GSLFunctionMap.all`.
- `register_gsl_backends` calls `Capability.init(allocator, ...)` → remove allocator param.

GSL's `GSLAdapter.validateGSLInput` is already heap-free (length comparisons). No changes needed there.

## Caller Ownership Model

```
Caller (application / host):
  ├── Owns ALL memory buffers
  │   ├── string_buf: [MaxStringTable]u8
  │   ├── formulas_buf: [MaxFormulas]FormulaEntry
  │   ├── capabilities_buf: [MaxCapabilities]Capability
  │   ├── result_buf: [MaxResultElements]f64 (per-call, reused)
  │   ├── provenance_buf: [MaxProvenanceEntries]ProvenanceRecord
  │   ├── overrides_buf: [MaxOverrideOps]BackendPolicy
  │   ├── cycle_colors: [MaxFormulas]u8 (per-call)
  │   ├── dep_queue: [MaxDepQueue]usize (per-call)
  │   └── scratch: [MaxResultElements]f64 (per-call)
  │
  └── Calls Yamori with buffer pointers:
      yamoriInit(
          string_buf, string_buf.len,
          formulas_buf, MaxFormulas,
          capabilities_buf, MaxCapabilities,
          overrides_buf, MaxOverrideOps,
      )

Yamori (library):
  ├── Never calls gpa.alloc, gpa.dupe, gpa.create
  ├── All functions take buffer pointers + capacities
  ├── FixedBufferAllocator wraps caller buffers when allocator interface needed
  ├── All errors propagate to caller (no swallowed allocations)
  └── No deinit needed — caller frees everything
```

## What This Enables

1. **Zero library-owned heap** — Yamori never allocates. Every buffer is caller-owned.
2. **Deterministic timing** — no malloc latency, no fragmentation. Fixed buffer sizes only.
3. **Predictable memory** — peak memory = sum of all buffer capacities. No hidden allocations.
4. **No ownership bugs** — caller owns everything. Yamori just uses pointers.
5. **No deinit needed** — caller frees their buffers when done. No deferred chains.
6. **GSL computation is already zero-alloc** — pure `f64 → f64` on caller buffers.

```zig
    @as([*]u8, @ptrCast(&result_buf))[0..result_buf.len * @sizeOf(f64)],
);

// Scratch buffers:
var scratch: [MaxResultElements]f64 = undefined;

// Provenance:
var prov_buf: [MaxProvenanceEntries]ProvenanceRecord = undefined;
var lengths_buf: [MaxProvenanceInputLengths]usize = undefined;
var prov: ProvenanceBuffer = undefined;
provenanceInit(&prov, &prov_buf, MaxProvenanceEntries, &lengths_buf, MaxProvenanceInputLengths);
```

**What this eliminates from every test:**
- `const gpa = std.testing.allocator;`
- `defer reg.deinit();`
- `defer cap.deinit(gpa);`
- `defer formula.deinit(&formula);`
- `try std.testing.expectError(error.OutOfMemory, ...)` — this is replaced by buffer capacity assertions

**What this adds to every test:**
- Buffer declarations (stack-sized, compile-time known)
- Init function calls (zero alloc)

**Net effect:** Tests get slightly longer (more setup lines) but simpler (no defer chains, no error handling for allocations). Total test LOC increases ~10-15% due to setup, decreases ~20% due to removed defer/errdefer/OutOfMemory checks.
