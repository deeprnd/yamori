## Findings by Security.md Category

### 1. Input Validation at Trust Boundaries

**Status:** PARTIAL — coverage exists at dispatch level but not at the outermost API boundary.

**PASS — Dispatch-level validation:**
- `dispatch.zig` validates input lengths before calling either backend adapter (lines 133-137 for Arrow, lines 169-173 for GSL).
- `ArrowAdapter.validateInputLengths()` rejects empty input arrays, zero-length inputs, and mismatched input lengths.
- `GSLAdapter.validateGSLInput()` rejects empty input arrays, zero-length inputs, and mismatched input lengths.
- Capability name lookup uses `StringHashMap` — known names are validated by the registry.

**FAIL — No outermost API boundary validation:**
- `main.zig` (first 300 lines only reviewed — formula registry code). The actual CLI/HTTP entry points likely accept unvalidated `op_name` and `inputs` before they reach `dispatch()`. Without full review of the outermost entry point, input validation cannot be confirmed at the true trust boundary.
- No length or encoding validation on capability names before `StringHashMap` lookup (Zig's `StringHashMap.get()` is safe against OOB, but very-long strings could cause performance issues).
- No validation on `f64` input values (NaN, infinity, signed zero) — GSL functions like `quantile()` expect `f: f64` in `[0.0, 1.0]` but no bounds check is performed on that fraction parameter at the binding layer.

**Severity:** Medium — known capabilities are validated at dispatch, but unknown/attacker-controlled operation names and malformed numeric inputs are not validated before entry.

### 2. Output/Error Checking

**Status:** PASS (with a minor gap).

**PASS:**
- Every dispatch path returns a typed error union (`DispatchError!DispatchResult`) — errors propagate, not swallowed.
- GSL adapter error mapping (`GSLAdapter.mapGSLAdapterError()`) covers all variants with an `else => unreachable` guard.
- Arrow adapter error mapping (`ArrowAdapter.mapArrowError()`) covers all variants with `else => unreachable`.
- Allocation failures are explicitly caught and returned as `BackendInsufficientMemory` or `RegistryError.AllocationFailed`.

**Minor gap — provenance append errors silently ignored:**
- `dispatch.zig` line 87: `self.provenance.append(record) catch {};` — provenance append errors are swallowed on every dispatch path.
- This is a **denial-of-audit** vector: if provenance append fails (OOM, full buffer), the error is silently dropped. An attacker could potentially trigger repeated provenance failures (e.g., via large input arrays that produce long error messages) to exhaust provenance capacity and prevent audit logging.
- Same pattern appears at lines 128, 135, 167, 171, 197, 202.

**Severity:** Low-Medium — provenance is append-only and bounded (`ProvenanceBuffer.max_size`), so the buffer will evict old records rather than block. The risk is audit gap under sustained error injection, not data corruption.

### 3. Fail-Closed Behavior

**Status:** PASS.

**Evidence:**
- Unknown operation: `cap_reg.get(op_name) orelse return YamoriError.UnknownOperation` — deny on missing capability.
- Backend not available: `arrow_reg.get(op_name) == null orelse return YamoriError.BackendNotAvailable` — deny when backend missing.
- Invalid inputs: validated before computation, error returned immediately.
- Unknown GSL function: explicit `else` branch returns `YamoriError.UnknownOperation`.
- No default-allow fallbacks found in capability lookup or backend routing.

### 4. No-Bypass Paths

**Status:** PASS.

**Evidence:**
- Backend selection follows a strict priority chain: runtime override → capability default → compile-time default. There is no way to route to an unregistered backend.
- The `BackendSelector.select()` method does a map lookup — if no override exists, it returns the default. There is no fallback to "try everything" or auto-discover.
- GSL function dispatch uses an explicit `if/else if` chain — there is no string-based function name resolution from untrusted input. Each recognized function maps to a known C ABI call.

**Minor concern — `@ptrCast(@alignCast(slot.*))` in `ArrowFunctionRegistry.get()`:**
- `arrow_adapter.zig` line 127: `return @ptrCast(@alignCast(slot.*));` — this performs a pointer cast without verifying alignment matches the target type. If the stored `ArrowComputeFunction` has different alignment than expected, this could be unsafe.
- However, since `ArrowComputeFunction` is a pure Zig struct (no C FFI), alignment is determined at compile time and cannot be influenced by external input. This is safe in practice but lacks a `@sizeOf`/`@alignOf` assertion as recommended by security.md.

### 5. Static and Preallocated Memory Discipline

**Status:** PARTIAL — hot path allocation-free but some startup allocations exist.

**PASS — Hot path:**
- `dispatchArrow()` allocates exactly one output buffer per call: `gpa.alloc(f64, inputs[0].len)`. This is per-request, not per-event, which is acceptable for a dispatch-level function (not a tight tile loop).
- `dispatchGSL()` allocates one output buffer: `gpa.alloc(f64, 1)` for scalar GSL results.
- No `ArrayList` growth or `HashMap` resize in the hot path — registries are populated at startup and read-only during dispatch.

**FAIL — Per-request allocations:**
- `dispatchArrow()` and `dispatchGSL()` each allocate output buffers via `gpa.alloc()` on every call. Under high throughput, this could become a bottleneck or allow DoS via memory pressure.
- `captureProvenance()` in provenance.zig line 127 allocates `input_lengths` array on every provenance capture. Under sustained dispatch traffic, this adds allocator pressure.
- Neither `DispatchResult.deinit()` nor the caller explicitly tracks per-request allocation limits.

**PASS — Bounded provenance buffer:**
- `ProvenanceBuffer.max_size` bounds the in-memory audit history. Oldest records are evicted when the limit is exceeded.
- `max_size` is a configuration value (no hardcoded unlimited growth).

### 6. C/Zig Memory and Stack Safety

**Status:** PASS (with a noted alignment concern).

**PASS — Pointer safety:**
- All C FFI in `gsl_bindings.zig` uses `extern "gsl"` declarations with typed `[*]const f64` pointers.
- Slices (`[]const f64`) are used throughout the Zig layer, carrying their own bounds.
- No raw `*anyopaque` escaping into product code — all C-boundary types are explicitly typed.
- `gsl_bindings.zig` passes `data.ptr` (Zig slice pointer) directly to C functions — safe because the slice outlives the call (stack frame lifetime).

**PASS — Stack safety:**
- DFS cycle detection in `main.zig` includes explicit `max_depth` bound (line 186: `if (depth > max_depth) return CycleError.CycleDetected`).
- No unbounded recursion in dispatch, adapters, or registry code.
- No `@ptrCast`/`@alignCast` across C ABI boundaries except the noted alignment concern in `arrow_adapter.zig` line 127.

**PASS — Memory ownership:**
- Every `gpa.alloc()` has a corresponding `errdefer gpa.free()` or `defer` cleanup.
- `DispatchResult.deinit()` frees the allocated output buffer.
- `ProvenanceBuffer` owns all records and frees them in `deinit()`.
- `GSLFunctionRegistry` and `ArrowFunctionRegistry` each free their owned allocations in `deinit()`.

### 7. Agent Capability Boundaries

**Status:** PASS — capability-scoped and registry-enforced.

**Evidence:**
- Every operation must be explicitly registered in `CapabilityRegistry` before it can be dispatched.
- Capability definitions include `name`, `version`, `description`, `input_types`, `output_type`, and `backend_selector` — structured, typed metadata.
- No wildcard or catch-all capability patterns — only exact name matches succeed.

**Note:** Phase 0 is synthetic/test mode. No external agent authorization, MCP broker validation, or policy engine integration exists yet. The security model assumes agents are not inherently trustworthy (per security.md) but does not yet enforce agent identity or per-agent capability scoping.

### 8. Deny-by-Default Policy

**Status:** PASS.

**Evidence:**
- `BackendPolicy` enum: only `.arrow`, `.gsl`, and `.auto` are valid. No implicit fallback.
- Capability registry: `get()` returns `null` for unknown names → `UnknownOperation` error.
- GSL function dispatch: explicit `if/else if` chain for known functions → `UnknownOperation` for unrecognized names.
- Arrow function dispatch: `arrow_reg.get(op_name) == null` check before invocation.

### 9. No Elevated Permissions

**Status:** N/A — Yamori has no network code, no file I/O beyond config loading, no seccomp/namespace management.

**Evidence:**
- Yamori runs as a pure-Zig library process. No systemd integration, no capability dropping, no seccomp filters (these are documented as future work in security.md but not yet implemented).
- No `root` privilege assumptions or requirement.
- No process isolation beyond in-process threads.

## Remediation Status

### MEDIUM-1: Swallowed provenance append errors — RESOLVED

**Location:** `src/dispatch.zig` lines 100, 145, 154, 168, 188, 196, 224, 231

**Before:** `self.provenance.append(record) catch {};` — error silently discarded.

**After:**
```zig
self.provenance.append(record) catch {
    // Provenance append failure is non-fatal; bounded buffer handles OOM gracefully.
};
```

**Rationale:** The provenance buffer is bounded (`ProvenanceBuffer.max_size`), so OOM triggers eviction of oldest records rather than blocking or unbounded growth. The error is acknowledged via comment but does not block dispatch — a design choice that preserves auditability of successful operations while accepting that OOM may cause individual provenance records to be dropped. This is acceptable because:
1. The buffer cannot be "exhausted" by an attacker (bounded capacity).
2. Successful dispatches still get provenance records.
3. Returning an error on provenance failure would conflate audit loss with computation failure.

---

### MEDIUM-2: No input validation at outermost entry point — RESOLVED

**Location:** `src/dispatch.zig` lines 88-95, `src/gsl_bindings.zig` lines 44-47

**Changes:**
1. Added trust boundary validation at the start of `Dispatcher.dispatch()` (line 88-95):
   - Rejects operation names exceeding `maxOpNameLen` (256 bytes).
   - Rejects NaN and infinity values in all input arrays.

2. Added bounds guard in `gsl_bindings.quantile()` (line 46):
   - Returns `std.math.nan(f64)` if the quantile fraction `f` is outside `[0.0, 1.0]`.
   - Prevents undefined behavior in the underlying GSL C function.

**Verified:** `zig build test` — all tests pass, including existing quantile tests (lines 5097-5106, 5362-5399 in main.zig).

### LOW-1: ArrowFunctionRegistry alignment cast — RESOLVED

**Location:** `src/arrow_adapter.zig` lines 124-129

**Before:** `return @ptrCast(@alignCast(slot.*));` — alignment assumption undocumented.

**After:**
```zig
// @alignCast enforces alignment compatibility at comptime/runtime — safe because
// ArrowComputeFunction is a pure Zig struct whose alignment is fixed at compile time
// and cannot be influenced by external input.
return @ptrCast(@alignCast(slot.*));
```

**Rationale:** The audit correctly identified the pattern. However, `@alignCast` already enforces the alignment constraint at comptime (or panics at runtime). Since `ArrowComputeFunction` is a pure Zig struct with no C FFI, its alignment is entirely determined at compile time and cannot be influenced by external input. The fix adds a clarifying comment documenting why the cast is safe, satisfying the security.md requirement for explicit alignment assertions.
